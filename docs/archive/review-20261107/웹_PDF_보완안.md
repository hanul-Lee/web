# 이한울 포트폴리오 재검토 · 웹 반영 및 PDF 보완안

검토일: 2026-11-07

검토 기준: 11월 4일 채용 리뷰, `최최종/0.web`의 홈·상세 10개·공통 코드, 다운로드 PDF 26쪽. 기존 채용 공고의 현재 모집 여부는 재검증하지 않았으며, 아래 내용은 제출 자료 자체에 대한 편집·설계 검토다. PDF는 원본을 유지하고 보완 원고를 작성했다.

## 1. 이번 판단

B2B 업무 서비스라는 포지션은 이미 분명하다. 이제 더 필요한 것은 프로젝트 수가 아니라 **업무 과업 → 본인의 선택 → 적용 화면 → 확인된 결과**를 짧게 연결하는 증거다. 배포·미사용·재구성 여부를 구분하는 기존 문구는 유지한다.

기존 리뷰의 일부 제안은 PDF에 이미 반영되어 있다. 6쪽에는 기획 요청과 본인의 표현 범위가, 7쪽에는 지도에서 자료를 찾는 순서가, 10쪽에는 내부 의견과 실사용이 분리되어 있다. 따라서 이 내용을 새로 반복 추가하기보다, 더 앞에서 읽히게 재배치하고 화면의 읽기 크기를 키우는 것이 우선이다.

수치, 사용자 수, 효율 향상률, 직접 인터뷰, Figma 라이브러리 운영 경험 등 확인되지 않은 사실은 추가하지 않았다. `.impact-flow strong` 및 상세 CSS는 변경하지 않았다.

## 3. PDF에서 우선 해결할 사항

### P0 · 공통 UI 기간 불일치

- PDF 20쪽: **2024.05–2024.07**
- 웹 공통 UI 상세: **2024.05–2024.10**
- 작업 기록으로 확인한 뒤 두 매체를 통일해야 한다. 어느 쪽이 맞는지는 현재 자료만으로 결정할 수 없다.
- 제작과 후속 적용 기간이 다르다면 `초기 가이드 제작 2024.05–07 / 후속 적용·정리 2024.08–10`처럼 구분할 수 있지만, 이 문구도 실제 기록 확인 후 사용한다.

### P0 · 텍스트 검색·복사가 되지 않음

현재 PDF는 26쪽 모두 텍스트 추출 결과가 0자다. 화면상 글자가 보이더라도 이름·역할·프로젝트명을 검색하거나 복사할 수 없다. 원본 편집 도구에서 제목·본문을 텍스트로 유지한 PDF로 다시 내보내는 것이 우선이다. 기존 PDF 위에 추정 OCR을 무조건 덧붙이는 방식은 오인식 가능성이 있어 우선안으로 삼지 않는다.

재출력 수락 기준: 이름, ‘통합 관리 플랫폼’, ‘TBM’, ‘공통 UI’를 검색할 수 있고 복사한 한글이 깨지지 않을 것. 기존 목차·홈·연락처 링크와 책갈피도 보존할 것. 현재 약 17.9 MB이므로 지원처 용량 제한에 맞추되 본문과 UI 확대 가독성을 유지할 것.

### P1 · 표지의 두 번째 문장을 배포 경험으로 교체

현재 표지는 B2B 포지션 다음에 HTML·CSS·SCSS·JS를 강조한다. 아래 두 줄로 바꾸고 기술은 프로필 역량에 둔다.

> B2B 업무 서비스의 정보 구조와 UI를 설계합니다.
>
> 지도 기반 통합 플랫폼과 현장 안전 기록(TBM)의 설계·배포 경험을 가진 디자이너 이한울입니다.

프로필의 전체 경력과 B2B 경력은 기존 재직 기간을 유지한다. ‘B2B 5년’처럼 실제 기간을 넘겨 반올림하지 않는다.

### P1 · 플랫폼 4–10쪽: 순서 개선과 근거 밀도

- 4쪽: 업무 한 줄과 담당 범위, 배포 상태를 유지한다. ‘기획의 현장 설명·사업 관리 구분을 메뉴 UI로 구현’이라는 역할 표현을 홈과 통일한다.
- 5쪽: 현재의 큰 텍스트 상자 세 개를 압축한다. 이미 7쪽에 있는 탐색 흐름을 앞당겨 **위치 확인 → 업무 메뉴 선택 → 자료 유형 탐색**을 보여준다.
- 6–7쪽: 분류를 만든 사람과 UI 표현을 정한 사람을 구분한다. 기존 번호 주석은 살리고 화면의 해당 영역을 더 크게 보여준다.
- 8쪽: 메뉴 비교는 유지한다. 비교 기준은 메뉴 구분·지도 맥락의 연속성으로 제한하고, 인지 속도 개선·탐색 시간 단축은 측정 없이 주장하지 않는다.
- 9쪽: 영상 탐색은 대표 과업에 필요한 만큼만 유지한다. 설명이 겹치면 보조 사례로 축약한다.
- 10쪽: 이미 있는 ‘직접 담당 / 내부 동료 의견 / 실제 활용’ 구분을 유지한다. 추가 자료가 있다면 의견을 받은 시점·경로와 반영 화면을 덧붙인다.

권장 요약 원고:

> 기획에서 나눈 현장 설명·사업 관리 메뉴를 지도 위에서 구분할 수 있도록 UI를 설계했습니다. 위치 확인에서 업무 메뉴와 자료 유형 선택으로 이어지는 화면을 퍼블리싱했습니다. 배포 후 실제 사용됐으며, 메뉴 구분에 관한 내부 동료의 의견을 받았습니다.

### P1 · TBM 11–15쪽: 작성·서명·열람을 혼동하지 않게

- 11쪽: 모바일 현장 작성과 웹 기록 입력·보관이라는 사용 환경을 먼저 제시한다.
- 12쪽: 종이 기록의 문제를 반복 설명하기보다 13쪽으로 이어지는 입력 항목의 대응 관계를 보여준다.
- 13쪽: 작성일·출역 인원·확인 상태·작성하기 버튼을 확대한다. 화면에 드러난 흐름만 설명한다.
- 14쪽: 서명은 **마이페이지에서 입력·변경·저장**하는 흐름이다. 일지마다 전자서명을 완료하는 승인 프로세스처럼 확대 해석하지 않는다. 서명 저장 완료 화면과 일지 확인 상태는 별개로 표현한다.
- 15쪽: 담당자 요청 → 사이트 내 파일 열람 추가 → 본인의 디자인·퍼블리싱 → 개발자를 통한 의견 전달이라는 협업 사슬을 한 줄로 붙인다.

권장 추가 문구:

> 담당자는 자료를 각자의 PC에서 따로 열기보다 사이트 안에서 확인하기를 원했습니다. 이에 PDF·HWP 파일 열람 UI의 디자인·퍼블리싱을 추가했습니다. 사용자 의견은 개발자를 통해 전달받았으며, 이용률과 업무 시간 변화는 측정하지 않았습니다.

### P1 · 공통 UI 20–23쪽: 재구성 예시에서 적용 근거로

현재 색상·입력·검색 상태 설명은 갖춰져 있다. 부족한 것은 동일한 요소가 실제 작업에 어떻게 연결되었는지를 확인할 한 사례다.

추가 페이지를 계속 늘리기보다 22–23쪽을 ‘요소 1개’ 중심으로 묶는다: 검색 입력의 상태 목록 → 상태별 모습 → 구현 기준 → 적용 화면의 같은 요소 표시. 실제 자료를 공개할 수 없다면 익명화하되 ‘당시 산출물 익명화’와 ‘포트폴리오용 신규 재구성’을 구분한다.

Figma variant·property 화면, 실제 SCSS 참조, 개발 전달 메모가 있는 경우에만 증빙으로 추가한다. 현재 설명용 팔레트·코드 예시를 조직 공용 디자인 시스템 운영 증거로 단정하지 않는다.

### P2 · ERP와 추가 작업 분량

ERP 16–19쪽은 최종 미사용 사실을 유지하며 조회 범위, 요약·상세, 상태 표현으로 압축할 수 있다. 제공 형식이 PDF로 바뀐 경험은 ‘초기에 산출물 형식을 합의할 필요’를 배운 사례로 연결한다.

B2B 제출본에서는 인트라넷·칸반의 분량을 늘리지 않는다. B2C·모바일 직무에서는 웹에 기재된 댕냥실록을 선택적으로 넣되 출시 링크·역할·출시 후 변경 기록이 준비되면 편성한다. 앱 링크는 실제 앱의 식별과 공개 여부를 확인한 뒤 연결한다.

## 5. 다음 개정의 권장 구성

B2B 기본 제출본은 18–20쪽 정도로 압축하는 안을 제안한다. 표지·프로필·목차 3쪽, 플랫폼 5쪽, TBM 5쪽, ERP 2쪽, 공통 UI 3쪽, 연락처 1쪽을 기본으로 하고 지원 직무에 따라 교체한다. 이는 필수 페이지 수가 아니라 중복 배경 설명을 줄이기 위한 편집안이다.

우선순위는 ① 기간 확인과 검색 가능한 PDF 출력 ② 표지 수정과 플랫폼 흐름 재배치 ③ 피드백 1건·공통 UI 적용 1건 증빙이다. 지원 건수나 회신 데이터가 없으므로 현재 자료만으로 무응답의 원인을 확정하지 않는다.
