## 페이지별 본문·이미지·배치

### 01쪽 — 유지

표지의 ‘업무를 이해하고, 화면과 구현으로 연결합니다.’가 본문 사례의 공통점을 잘 설명합니다. 작은 설명이나 프로젝트명을 더 늘리지 않습니다.

### 02쪽 — 역할 표현과 중복 분류 정리

- `주요 성과 : 대규모 통합 플랫폼 UX 리드` → `주요 경험: 통합 플랫폼 메뉴·지도 UI 설계 및 퍼블리싱`
- 아래 경력의 `주요 성과 : 스카이오토넷 웹사이트 UI·퍼블리싱 담당` → `주요 작업: 스카이오토넷 웹사이트 UI 설계·퍼블리싱`
- `GDWEB 소개 페이지 누적 조회 10만 이상`은 삭제 권장. 남긴다면 ‘외부 소개’로 별도 분리하고, 사이트 이용자 수나 본인 설계의 효과처럼 읽히지 않게 합니다.
- `직무 기술`과 `업무 역량`의 내용이 겹칩니다. 각각 `주요 경험`, `사용 도구`로 바꾸면 분류가 선명해집니다.
- 사용 도구 표기: `Figma · HTML · CSS/SCSS · JavaScript · Git / React 학습 중`. React의 학습 상태는 현재처럼 구분합니다.
- 학력은 졸업장 기준의 기관·전공·학위 명칭과 일치하는지 확인 후 제출합니다. 이미지에 적힌 내용만으로 다른 명칭을 단정해 바꾸지는 않습니다.

### 03쪽 — 목차의 결과 표현 정리

배치와 프로젝트 이동 안내는 유지합니다. ERP 행의 결과는 `웹 설계안 최종 미사용`으로 적으면 ‘웹 설계안 최종 미채택’보다 16·19쪽의 설명과 일치합니다. 공통 UI의 결과 문구는 `컬러와 일부 UI 재사용`으로 맞춥니다.

### 04쪽 — 플랫폼 표지 유지

기획 요청을 반영한 메뉴·지도 UI와 퍼블리싱이라는 담당 범위가 명확합니다. 하단 ‘결과’는 `배포 후 실제 사용 · 전시 활용`처럼 본문 10쪽과 용어만 맞춥니다.

### 05쪽 — 제목을 메뉴 문제 중심으로 정리

큰 제목 교체안:

> 흩어진 자료를 살펴보고, 기능이 구분되는 메뉴를 설계했습니다.

작은 제목은 `업무 배경과 설계 과제`. 세 카드 제목은 `자료 인계 상황 / 초기 메뉴의 문제 / 담당한 UI 설계`로 정리합니다. 자료의 최종본 혼동을 해결한 작업처럼 확장하지 않고, 메뉴 구분이 실제 설계 과제였다는 흐름을 유지합니다.

하단 문구 교체안:

> 자료 인계 상황을 업무 배경으로 파악하고, 메뉴 구분과 지도 탐색 UI를 설계했습니다.

카드 상단을 현재보다 위로 올려 제목과 본문 사이의 큰 공백을 줄입니다.

### 06쪽 — 기획 방향과 본인 판단의 구분 유지

작은 제목은 `메뉴 구분과 UI 설계`로 교체합니다. 두 하단 카드의 구분은 현재처럼 유지하되 오른쪽을 `제가 판단한 UI 표현`으로 바꾸면 ‘메뉴 구분 자체를 기획했다’는 의미와 분리하기 쉽습니다.

가운데 지도 이미지는 7·9쪽에서도 반복됩니다. 이 페이지에서는 메뉴 구분이 보이는 부분을 확대하고, 7쪽에서 전체 탐색 흐름을 보여주는 편이 좋습니다.

### 07쪽 — 흐름을 선과 번호로 연결

작은 제목은 `지도에서 자료로 이어지는 흐름`. `① 지도 → ② 업무 메뉴 → ③ 자료 유형`의 연결을 화면 번호와 우측 설명에 동일하게 사용합니다. 현재처럼 전체 화면을 보여주는 역할은 이 페이지에 남깁니다.

### 08쪽 — 시안 비교 유지

작은 제목과 큰 제목은 유지합니다. C안의 선택 테두리를 프로젝트의 강조색으로 통일합니다. 하단의 실험 관련 문장은 `당시 제작한 메뉴 디자인 시안 비교`로 간결하게 정리할 수 있습니다. 실제 사용자 테스트 결과를 추가로 주장하지 않습니다.

### 09쪽 — 7쪽과 화면의 역할을 구분

작은 제목은 `자료 유형별 메뉴 진입점`. 현재 큰 지도 화면이 7쪽과 거의 같아 반복으로 보입니다.

- 7쪽: 전체 탐색 흐름.
- 9쪽: 하단 메뉴와 시뮬레이션 유형의 실제 확대 발췌.

추가 캡처가 있다면 `도면 / 시뮬레이션 / 실감형 모델`의 진입 화면을 나란히 보여주는 구성이 좋습니다. 현재 캡처 하나만 쓴다면 실제 보이는 시뮬레이션 선택과 하단 메뉴만 발췌하고, 캡처에 없는 화면의 결과를 보여주는 것처럼 설명하지 않습니다.

우측 ‘본인 담당’은 4·6·10쪽과 중복이므로 이미지 아래 한 줄로 줄여도 됩니다.

### 10쪽 — 결과 세 가지의 읽는 순서 정리

작은 제목은 `배포 결과와 협업`. 카드 순서를 `배포와 실제 사용 / 내부 동료 의견 / 담당 범위와 협업`으로 바꾸면 결과가 먼저 읽힙니다. 내부 동료의 의견이라는 출처는 유지합니다.

카드를 위로 당기고 첫 번째 카드의 글자 수를 나머지 카드 수준으로 줄입니다. 4·6쪽에서 설명한 역할 전체를 반복할 필요는 없습니다.

### 11쪽 — TBM 표지 유지

웹과 모바일을 함께 보여주는 현재 표지는 유지합니다. 웹 이미지는 여기서 이미 쓰고 있으므로 같은 이미지를 장식 목적으로 한 번 더 반복할 필요는 없습니다. 추가한다면 15쪽의 실제 파일 열람 기능처럼 새로운 내용을 보여줘야 합니다.

### 12쪽 — 문제와 대응을 짝지어 제시

작은 제목 교체안은 `수기 기록에서 찾은 설계 과제`입니다.

카드 제목을 `보관과 조회 / 내용 입력과 판독 / 현장 작성`으로 맞추면 문제와 대응을 함께 설명하기 좋습니다. 현재 종이 일지와 확대 발췌는 유지합니다. 이 페이지에 웹 전체 화면까지 넣으면 문제 설명의 초점이 흐려지므로 권장하지 않습니다.

### 13쪽 — 작은 제목과 ③ 위치 수정

작은 제목은 `일지 확인과 작성 진입`으로 교체합니다. 현재 큰 제목은 유지해도 됩니다.

- ①: 작성일·출역 인원.
- ②: 담당·소장 확인 상태.
- ③: 하단 ‘작성하기’ 버튼으로 이동.

지금 ③은 ‘주관자’ 줄에 있어 우측 ‘작성 진입’ 설명과 맞지 않습니다. 하단 캡션 `[TBM]`은 `모바일 일지 · 작성 정보와 확인 상태`로 바꿉니다.

실제 작성 폼 캡처가 있다면 ‘작성하기’ 다음에 무엇을 입력하는지 보여주는 보조 화면을 추가할 수 있습니다. 다만 이는 모바일 화면 보강이며, 웹 담당 범위를 보여주는 자료는 아닙니다.

### 14쪽 — 서명 흐름은 유지

작은 제목은 `서명 입력과 저장 확인`으로 바꿀 수 있습니다. 서명 저장과 일지 전체 제출을 구분한 현재 설명은 유지합니다.

파란 단계 라벨은 휴대폰 내부 화면 위보다 이미지 카드의 상단 여백으로 옮기는 것이 좋습니다. 기기 상단과 화면 제목을 가리지 않게 하기 위한 배치 수정입니다.

### 15쪽 — 웹 화면 추가의 최우선 위치

작은 제목: `추가 요청과 웹 기능 확장`

현재의 세 개 가로 박스는 왼쪽 30~35% 너비의 짧은 설명으로 줄입니다. 오른쪽 65~70%에는 실제 웹 파일 열람 화면을 크게 배치합니다.

아래에는 `배포 후 실제 사용 · 사용자 의견은 개발자를 통해 전달받음`을 한 줄로 둡니다. 구체적 의견의 내용이 없는 현재 상태에서 긍정적인 평가 내용을 새로 만들지 않습니다.

이미지를 추가하면 현재의 ‘파일 열람 화면 캡처는 포함하지 않았으며’라는 하단 문장은 삭제합니다. 이미지가 준비되기 전에는 기존 도식을 유지합니다.

### 16쪽 — ERP 표지 유지

최종 웹 설계안이 사용되지 않았다는 설명은 이미 들어가 있습니다. 하단 상태만 `PDF 제공으로 변경 · 웹 설계안 최종 미사용`으로 통일합니다.

### 17쪽 — 비교의 대상과 크기 정리

작은 제목은 유지합니다. 실제 화면 안의 빨간 설명과 파란 설명, 카드 위 파란 라벨이 중복되므로 각 카드에 라벨 한 번만 남기는 편이 좋습니다.

하단 문구는 `기존 행 단위 자료와 웹 설계안의 정보 구성 비교`로 간결하게 정리할 수 있습니다. 두 캡처를 같은 배율로 맞추기보다 비교할 열·요약 영역이 읽히도록 필요한 부분을 발췌합니다.

### 18쪽 — 조회 범위와 화면 영역을 연결

현재 배치를 유지한다면 작은 제목은 `조회 범위와 정보 위계`가 맞습니다. ‘흐름’을 유지하려면 화면에 `① 조회 조건 → ② 주요 수치 → ③ 상세 내역`을 표시해야 합니다.

왼쪽의 세 줄 설명을 좁은 영역으로 줄이고 ERP 화면을 넓힙니다. 제목 아래 빈 공간을 줄이면 화면을 확대할 여유가 생깁니다. 실제 캡처는 전사 화면 중심이므로 전사·프로젝트·개인 화면을 모두 보여준 것처럼 캡션을 쓰지는 않습니다.

### 19쪽 — 상태 표현과 결과를 구분

작은 제목 교체안은 `상태 표현과 프로젝트 결과`입니다. 큰 제목의 ‘현재 범위’를 앞 카드와 맞춰 `조회 범위`로 바꿉니다.

큰 제목 교체안:

> 조회 범위, 비용 합계, 초과 상태를 구분했습니다.

가운데 `9/8h`는 상태 표시 예시로 유지합니다. 오른쪽은 `최종 결과와 다음 작업의 기준`으로 제목을 정리하고, PDF로 제공 형식이 변경된 사실과 다음 작업에서 먼저 확인할 조건을 짧게 적습니다.

### 20쪽 — 표지의 범위를 본문과 통일

작은 영문 태그는 `PROJECT 04 · 공통 UI 기준 · 웹 가이드`로 정리하는 편이 좋습니다. `Brand · Foundation · Component · Resources`는 본문에서 상세하게 다루지 않는 범위까지 읽힐 수 있습니다.

하단 ‘사용 범위’의 `컬러와 일부 UI 요소 재사용`은 유지합니다.

### 21쪽 — 변수와 가이드의 연결 유지

작은 제목은 `컬러 변수와 웹 가이드`로 정리할 수 있습니다. 코드와 실제 가이드의 컬러 단계가 보여 현재 두 이미지 구성이 적절합니다.

하단 문구 교체안:

> 공통 컬러를 SCSS 변수와 웹 가이드로 정리하고, 컬러와 일부 UI를 프로젝트에 재사용했습니다.

별도 적용 사례가 있다면 해당 화면을 보조로 추가할 수 있지만, 현재 페이지에는 정의와 가이드 비교만으로도 충분합니다.

### 22쪽 — 재사용 사례 대신 상태·구현 기준으로 명명

작은 제목은 `입력 UI의 상태와 구현 기준`으로 교체합니다.

- `현재 코드` → `SCSS 구현`
- `현재 가이드` → `입력 UI 가이드`

본문은 ‘당시 입력 가이드’라고 설명하면서 위 라벨에서는 ‘현재’라고 쓰고 있으므로 시점 표현을 맞춰야 합니다. 코드 이미지는 읽기 전용·편집 상태의 차이가 보이는 부분을 중심으로 발췌합니다. 하단의 실제 사용 범위 문구는 유지합니다.

### 23쪽 — 검색 요소임을 작은 제목에 명시

작은 제목은 `검색 입력의 상태와 배치`로 교체합니다. `가이드 구성` 라벨은 `검색창 배치 예시`로 바꿉니다.

하단 문구 교체안:

> 당시 검색 입력 가이드의 기본·포커스·입력 중·비활성 상태와 콘텐츠 상단 배치 예시입니다.

전체 컴포넌트 운영 성과를 측정하지 않았다는 설명은 매 페이지에서 반복하기보다 프로젝트 결과나 발표 설명에서 한 번 정리해도 됩니다. 이 페이지는 실제로 보여주는 가이드에 집중합니다.

### 24쪽 — 유지, 표기만 통일

작은 제목은 `추가 경험 · 모바일 인트라넷`. 미배포라는 상태와 실제 예약·근태 화면은 유지합니다. 캡션의 과정 표시는 `현황 확인 → 예약 입력`, `문서 선택 → 근태 신청`처럼 동사 중심으로 맞추면 읽기 쉽습니다.

### 25쪽 — 개인 프로젝트와 후속 과제의 분리 유지

작은 제목은 `추가 경험 · 개인 칸반 프로토타입`. AI의 도움을 받은 구현이라는 설명은 유지합니다. 하단 `수행 범위`는 `구현 범위와 다음 개선`으로 바꾸면 현재 내용에 더 정확합니다.

진행 기간의 ‘진행 중’은 실제 작업 상태에 맞춰 최종 제출 시 갱신합니다. 완료한 작업이라면 실제 종료 시점을 적습니다.

### 26쪽 — 유지

표지의 메시지와 연결되고 연락처도 모여 있어 현재 구성을 유지해도 됩니다. 실제 PDF의 이메일·웹사이트·목차 링크 동작은 PNG만으로 확인할 수 없으므로 최종 PDF에서 별도로 확인합니다.

## TBM 웹 이미지 추가 제안

| 우선순위 | 위치 | 필요한 실제 화면 | 보여줄 것 |
| --- | --- | --- | --- |
| 1 | 기존 15쪽 개편 | 사이트 안에서 PDF 또는 HWP 등 관련 파일을 열고 있는 화면 | 추가 요청이 실제 어떤 UI로 구현됐는지, 직접 맡은 파일 열람 기능 |
| 2 | 화면이 2장 이상 있으면 14쪽과 결과 페이지 사이에 새 웹 상세 페이지 | 파일 목록·선택 화면 + 열람 화면 | ‘파일 선택 → 사이트 내 열람’의 실제 흐름 |
| 3 | 웹 기본 UI의 담당 범위도 강조하려는 경우 새 웹 상세 페이지의 보조 화면 | 웹 TBM 일지 목록·상세 중 직접 참여한 부분 | 모바일 작성과 구분되는 웹 확인·관리 화면 |

한 장만 추가할 수 있다면 **15쪽에 실제 파일 열람 화면 한 장**이 가장 효과적입니다. 표지 11쪽에 웹 전체 화면이 이미 있으므로, 같은 전체 화면을 반복하기보다 파일 목록·열기 동작·열람 영역 중 핵심이 읽히는 캡처를 고릅니다.

권장 캡처 기준:

- 파일이 실제로 열린 상태를 중심으로 고릅니다. 목록만 있는 화면보다 추가한 기능이 분명합니다.
- 전체 브라우저 화면을 너무 작게 축소하지 말고, 선택한 파일과 열람 영역이 읽히도록 필요한 부분을 발췌합니다.
- 화면에서 확인할 수 있고 직접 담당한 요소에만 ①·② 번호를 붙입니다. 다운로드·검색·페이지 이동 같은 기능은 실제 구현 및 담당 여부를 확인한 뒤 설명합니다.
- 실제 이름·서명·전화번호·현장 내부 정보는 캡처 공개 범위에 맞춰 가립니다.
- 웹 일지 화면을 넣더라도 파일 열람 기능의 결과 화면과 구별합니다. 일지 전체 화면만으로 PDF·HWP 열람 기능의 증거를 대신하지 않습니다.

새 페이지를 추가하면 목차의 ERP·공통 UI·추가 경험 시작 쪽수와 각 PDF 이동 링크도 함께 갱신합니다.

## 공통 편집 기준

- 작은 제목은 페이지 내용을 이름 붙이는 짧은 명사구로, 큰 제목은 핵심 판단이나 작업을 설명하는 문장으로 씁니다.
- 왼쪽 작은 제목과 오른쪽 상단 경로의 마지막 항목을 같은 이름으로 맞춥니다.
- `추가 경험`, `읽기 전용`, `프로젝트 1`처럼 띄어쓰기를 통일합니다.
- 파란 설명 라벨은 카드 윗선에서 같은 높이로 맞추고 이미지 속 중요한 제목·입력 영역을 가리지 않게 합니다.
- 같은 프로젝트의 반복 캡처는 전체 흐름·부분 확대·대안 비교 중 각기 다른 역할을 맡도록 정리합니다.
- 효과 측정이 없는 곳에서 수치를 새로 만들 필요는 없습니다. 하단 설명은 실제 확인한 범위와 자료의 성격을 한 문장으로 적습니다.
