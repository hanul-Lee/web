## 4쪽: 통합 플랫폼 담당 범위

**제목**
지도와 업무 자료를 연결한 통합 관리 플랫폼

**소개 문안**
현장·본사·외부 사용자가 필요한 자료를 확인하도록 공통 메뉴와 지도 중심 화면을 설계했습니다. 기획에서 제안한 ‘현장 설명 / 사업 관리’의 구분을 메뉴 UI에 반영하고, 지도 탐색 화면과 퍼블리싱을 담당했습니다. 플랫폼은 배포 후 실제 사용자가 이용했습니다.

**참여 정보**
- 담당: 메뉴 UI · 지도 탐색 UI · 퍼블리싱
- 협업: 개발자 · 기획자 · 엔지니어
- 기간: 2023.01 - 2023.12
- 상태: 배포 후 실사용

## 5쪽: 문제를 알게 된 계기

**제목**
자료는 흩어져 있었고, 메뉴의 구분도 모호했습니다.

**본문**
프로젝트를 처음 맡으며 많은 자료를 전달받고 기존 파일과 프로그램을 살펴봤습니다. 사람마다 서로 다른 파일을 가지고 있는 경우도 있어, 어떤 자료가 최종본인지 헷갈렸습니다. 초기 화면에서는 기능이 어느 분야에 속하는지 구분하기 어렵다는 문제도 있었습니다.

**세 개의 짧은 설명**
1. 자료 인계: 여러 파일과 기존 프로그램의 자료를 함께 살펴봐야 했습니다.
2. 최종본 혼동: 사람마다 가진 자료가 달라 최신 자료를 판단하기 어려웠습니다.
3. 이번 UI 과제: ‘현장 설명 / 사업 관리’의 구분과 관련 기능의 진입점을 화면에서 명확히 보여주는 데 집중했습니다.

**편집 주의**
최종본 혼동은 프로젝트를 접하며 알게 된 업무 맥락입니다. 메뉴 분리로 버전 관리까지 해결했다고 연결하지 않습니다. 별도의 버전 관리 기능과 확인 자료가 없다면 최신본 자동 관리·중복 파일 제거 등을 추가하지 않습니다.

## 6쪽: 기획 요청과 본인의 판단

**제목**
두 메뉴의 구분을, 지도 위에서 읽히도록 설계했습니다.

**본문**
디자인 작업 중 기획 측에서 ‘현장 설명 / 사업 관리’로 메뉴를 나누자는 요청을 받았습니다. 저는 이 구분을 메뉴 UI에 반영하고, 지도와 관련 기능으로 이어지는 화면을 구성했습니다.

**두 영역으로 구분**
- 기획에서 제안한 방향: 현장 설명과 사업 관리로 메뉴를 분리
- 본인이 비교·선택한 UI: 메뉴 영역을 구분하면서 지도 배경의 연속성을 유지하는 표현

**이미지 연출**
실제 메뉴를 크게 배치하고 두 메뉴 명칭을 표시합니다. 기능별 소속은 실제 화면에서 확인할 수 있는 범위만 적습니다. 사용자 조사로 분류 체계를 독자적으로 도출했다고 표현하지 않습니다.

## 8쪽: 대안과 선택

**제목**
메뉴는 구분하되, 지도는 끊지 않기

**도입 문안**
지도 위에서 메뉴를 사용하는 화면이라, 메뉴 영역의 구분과 지도 배경의 연속성을 함께 고려했습니다.

| 대안 | 시안을 보며 판단한 점 |
| --- | --- |
| 흰색 | 메뉴 경계는 선명하지만 지도와 분리되어 보임 |
| 검정 | 메뉴 영역의 존재감이 강하게 드러남 |
| 반투명 검정: 선택 | 메뉴를 구분하면서 지도 배경의 연속성을 고려 |

**하단 문안**
두 기준을 함께 고려해 반투명 검정안을 선택했습니다. 당시 시안은 메뉴 구성과 선택 상태도 다르므로, 동일 조건의 가독성 실험 결과로 소개하지 않습니다.

**이미지 연출**
세 시안의 지도·메뉴 부분을 같은 비율로 보여줍니다. 선택안만 얇은 테두리로 강조합니다. 비교 이미지와 설명이 한 화면에 들어가도록 긴 배경 설명은 줄입니다.

## 10쪽: 내부 피드백과 배포

**제목**
내부 동료에게는 메뉴 구분이 명확하다는 의견을 받았습니다.

**의견 요약**
“구분이 명확해졌고, 나뉘어 있어 사용하기 좋다.”

위 문장은 내부 동료에게 받은 의견의 요약입니다. 인터뷰 원문이나 현장 사용자 발언으로 표기하지 않습니다.

**배포 사실**
설계·퍼블리싱한 플랫폼은 배포되어 실제 사용자가 이용했습니다. 산출물은 프로젝트 시연과 내부 소통에도 활용했습니다.

**담당 범위**
기획의 메뉴 분리 요청을 UI에 반영하고, 지도 탐색 화면과 퍼블리싱을 담당했습니다. 정보 범위와 UI 기준은 개발자·기획자·엔지니어와 조율했습니다.

**확인 범위**
실제 현장 사용자의 의견은 직접 듣지 못했습니다. 내부 동료의 피드백과 실제 사용자의 사용성 검증을 구분합니다. 탐색 시간·클릭 수 변화는 측정하지 않았습니다.

## 11쪽: TBM 소개 보강

**소개 문안**
작업 전 안전 점검을 기록하는 TBM 일지를 웹·모바일 화면으로 설계했습니다. 모바일 일지·서명 화면의 기획·디자인과 웹 UI에 참여했습니다. 담당자의 추가 요청에 따라 사이트 내 파일 열람 기능의 디자인·퍼블리싱도 진행했습니다.

**참여 정보**
- 모바일: 일지·서명 화면 기획·디자인
- 웹: UI 참여 · 파일 열람 기능 디자인·퍼블리싱
- 협업: 개발자
- 상태: 배포 후 실제 사용자 이용

## 15쪽: 요청에 따라 달라진 범위

**제목**
일지를 올리는 기능에서, 관련 파일을 열어보는 기능까지.

**추가 요청의 배경**
초기 기획은 프로젝트 선택과 TBM 일지 작성·업로드였습니다. 담당자는 다른 파일도 각자의 PC에서 따로 열지 않고, 사이트 안에서 한 번에 확인하기를 원했습니다.

**추가한 내용**
사이트에서 PDF·HWP 등의 파일을 열어 확인하는 기능을 추가했습니다. 저는 이 기능의 디자인·퍼블리싱을 맡았습니다.

**비교 문구**
- 초기 기획: 프로젝트 선택 · TBM 일지 작성·업로드
- 추가 제작: 사이트 내 PDF·HWP 파일 열람
- 직접 담당: 추가 기능의 디자인·퍼블리싱

**배포와 확인 범위**
서비스는 배포 후 실제 사용자가 이용했습니다. 사용자 의견은 개발자를 통해 전달받았습니다. 파일 열람 기능의 이용률이나 작업 시간 변화는 측정하지 않았습니다.

**이미지가 준비되어 있다면**
실제 열람 화면 한 장을 크게 보여주고 담당 부분을 표시합니다. 파일 목록·열기 버튼·열람 화면 중 본인이 담당한 상세 요소는 확인 후 표기합니다. 지금 단계에서 열람 화면이나 피드백 장면을 새로 만들어 과거 작업처럼 넣지 않습니다.

**이미지가 없다면**
초기 기획과 추가 제작 범위를 비교하는 텍스트 도식으로 구성합니다. ‘기획 범위 변화’라고 명시하고 실제 UI 화면으로 소개하지 않습니다.

## 나머지 페이지에서 유지할 내용

- 16~19쪽 ERP: 제공 형식이 PDF로 변경되어 웹 설계안이 최종 사용되지 않았다는 사실을 유지합니다. 9시간 / 기준 8시간은 상태 표현 예시입니다.
- 20~23쪽 공통 UI: 재사용한 컬러와 일부 UI 요소를 구체적으로 보여줍니다. 조직 전체 디자인 시스템의 도입 성과로 확대하지 않습니다.
- 24쪽 인트라넷: 디자이너 팀 내부 작업·미배포 상태를 유지합니다.
- 25쪽 칸반: AI 보조 구현과 실제 사용자 평가 미실시를 구분해 표기합니다.

## 완성도를 더 높일 자료의 우선순위

| 우선순위 | 필요한 자료 | 추가되면 설명할 수 있는 것 |
| --- | --- | --- |
| 1 | TBM 파일 열람 기능의 실제 화면과 본인 담당 부분 | 요청이 어떤 UI로 구현됐는지 |
| 2 | 플랫폼 내부 의견을 받은 시점과 맥락 | 누가 어떤 화면을 보고 의견을 주었는지 |

| 4 | 현장 사용자에게 앞으로 확인할 탐색 과업 | 내부 피드백 이후의 검증 계획 |

새로운 사용성 검증을 진행한다면 ‘언제, 누구에게, 어떤 과업을, 무엇으로 확인했는가’를 기록합니다. 과거 프로젝트의 당시 검증 결과와 이후 포트폴리오 보강을 위한 검증은 시점을 구분합니다.

## 제출 전 점검

- 웹과 PDF에서 역할·기간·배포 상태·의견을 준 주체가 일치하는가?
- 담당자 요청과 본인의 UI 판단이 구분되는가?
- 설계 의도, 실제 기능, 받은 의견, 측정 결과가 구분되는가?
- 재구성 설명도와 실제 서비스 화면이 구분되는가?
- 최신 PDF로 교체한 뒤 다운로드 링크의 버전도 바꿨는가?
