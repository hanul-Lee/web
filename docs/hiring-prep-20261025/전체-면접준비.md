> 안녕하세요. 복잡한 업무를 사용자가 이해하고 처리할 수 있는 화면으로 만드는 디자이너 이한울입니다.

“토목·건축이 싫어서요”로 끝내지 않습니다. 산업에서 배운 역량 → 다음에 풀고 싶은 문제 → 해당 회사에서 기여할 지점으로 연결합니다. 실제 전환 이유가 다르면 위 대본의 동기를 본인 사실로 수정합니다.

## 7. 가장 강한 사례 40초: 플랫폼

> 초기 메뉴에서는 기능이 어느 업무에 속하는지 구분하기 어려웠습니다. 기획자가 현장 설명과 사업 관리로 나누는 방향을 제안했고, 저는 이를 UI로 구체화했습니다. 흰색·검정·반투명 검정안을 비교해서 메뉴 경계와 지도 배경의 연속성을 함께 고려한 반투명 검정안을 선택하고 퍼블리싱했습니다. 배포 후 실제 사용됐고, 내부 동료에게 구분이 명확하다는 의견을 받았습니다. 현장 사용자 대상 탐색 시간이나 클릭 수는 별도로 측정하지 않았습니다.

## 8. 두 번째 사례 40초: TBM

> 종이 기록을 웹과 모바일로 옮기는 서비스에서 모바일 일지·서명 화면을 기획하고 디자인했습니다. 작성일과 출역 인원, 담당·현장 책임자의 확인 상태, 작성 진입을 구분했습니다. 서명은 입력과 저장 완료를 별도 상태로 표현했습니다. 이후 담당자가 PC에서 따로 열던 자료를 사이트 안에서 보고 싶다고 요청해 파일 열람 UI의 디자인과 퍼블리싱도 맡았습니다. 서비스는 배포 후 사용됐고, 사용자 의견은 개발자를 통해 전달받았습니다.

## 9. 성과 수치가 없다는 질문

끝을 “못 했습니다”로 닫지 말고, **확인한 결과 → 측정 한계 → 다음 설계**로 닫습니다.

## 10. 6~7년 차인데 제품 경험이 부족하지 않나

> 제품 성장 지표를 반복 실험으로 개선해 온 경력자와 비교하면 그 경험의 깊이는 부족한 부분이 있습니다. 반면 복잡한 업무 요구를 정리하고 UI와 퍼블리싱, 개발 협의로 구체화한 경험은 바로 기여할 수 있는 영역입니다. 제가 가진 강점을 분명하게 가져가되, 초기부터 문제·성공 기준·확인 방법을 팀과 합의하는 방식으로 검증 역량을 보완하겠습니다.

## 11. ERP 미사용 설명

> 비용·인원 자료를 조회 조건, 주요 수치, 상세 내역으로 나눠 웹 UI를 설계하고 퍼블리싱했습니다. 다만 최종 제공 형식이 PDF로 바뀌어 웹 설계안은 사용되지 않았습니다. 이 사례에서 배운 점은 화면을 만들기 전에 사용자가 직접 조회해야 하는지, 정해진 보고서를 받아야 하는지와 최종 제공 형식을 먼저 합의해야 한다는 것입니다.

## 12. 디자인 시스템 질문

> 제가 한 일은 공통 컬러를 SCSS 변수로 관리하고, 입력·검색 UI의 상태를 웹 가이드로 정리한 것입니다. 컬러와 일부 UI를 디자이너의 디자인·프론트 작업에서 재사용했습니다. 전사 디자인 시스템을 구축하고 운영한 경험으로 확대해서 설명하지는 않겠습니다.

## 13. React·AI 질문

> HTML·CSS·SCSS와 JavaScript, Git을 작업에 사용하고 있고 React는 학습 중입니다. 개인 칸반은 제가 보드 UI를 설계하고 AI의 도움을 받아 카드 이동과 작업 생성을 구현한 프로토타입입니다. 제가 판단한 UX와 구현 보조를 받은 부분을 나눠 설명할 수 있습니다. React 실무 제품을 독립적으로 개발한 경험으로 말씀드리지는 않습니다.

실제로 사용한 JavaScript·Git 범위와 설명 가능한 코드는 본인이 확인해야 합니다. 할 수 있는 부분을 과도하게 축소하지도, 확인하지 않은 영역까지 넓히지도 않습니다.

## 14. 사용자 리서치 질문

> 현재 대표 사례의 근거는 인계받은 자료와 기존 화면 검토, 기획·개발 협의, 내부 동료 의견과 개발자를 통해 전달받은 사용자 의견입니다. 직접 현장 사용자를 대상으로 진행한 정식 인터뷰나 사용성 테스트 결과로 제시한 자료는 아닙니다. 다음에는 과업 관찰과 프로토타입 테스트를 통해 어떤 구간에서 사용자가 막히는지 직접 확인하고 싶습니다.

## 15. 기획자가 방향을 정했는데 본인의 기여는

> 메뉴를 두 분야로 나누자는 방향은 기획자의 제안입니다. 저는 그 구분을 화면에서 어떻게 보이게 할지 판단했습니다. 지도 위에서 메뉴 경계와 선택 상태를 표현하고, 세 시안을 비교해 반투명 검정안을 선택한 뒤 퍼블리싱했습니다. 방향을 제안한 사람과 UI 결정을 구체화한 제 역할을 구분하고 있습니다.

## 16. 시각 디자인 강점 질문

> 정보 구조뿐 아니라 그 구조가 실제 화면에서 읽히게 만드는 데 강점이 있습니다. 플랫폼에서는 배경과 메뉴 경계를, ERP에서는 선택 상태와 합계·초과 수치의 강조를, 반응형 웹에서는 제목과 제품 진입점의 위계를 다뤘습니다. 색과 간격의 선택을 사용자가 먼저 알아야 하는 정보와 연결해서 설명할 수 있습니다.

## 17. 모르는 질문을 받았을 때

> 그 부분은 직접 수행한 범위가 아니어서 단정하기 어렵습니다. 제가 담당한 것은 [범위]입니다. 지금 판단한다면 [확인할 정보]를 먼저 확인하고 [가설/선택]을 검토하겠습니다.

이 답변은 “모릅니다”를 피하려는 말이 아니라 **경험의 경계와 사고 방식**을 함께 보여주는 말입니다.

## 18. 마지막 한마디

> 오늘 말씀드린 경험의 공통점은 복잡한 업무를 이해하고, 사용자가 필요한 정보를 확인하고 다음 행동으로 이어가도록 화면을 구체화한 것입니다. 새로운 산업에서도 이 역량으로 빠르게 기여하고, 이후 사용자와 지표로 확인하는 개선 과정까지 책임 범위를 넓히고 싶습니다. 감사합니다.

## 19. 면접 직전 60초 점검

- 내 역할은 “기획 전부”가 아니라 실제 UI 결정과 구현 범위로 말한다.
- 성과는 배포·실사용과 피드백 경로까지. 측정하지 않은 수치는 만들지 않는다.
- ERP 미사용, 인트라넷 미배포, 칸반 미평가를 숨기지 않는다.
- 공개 재구성·가상 데이터와 실제 납품/운영 화면을 구분한다.
- 통합 플랫폼의 분산 자료 문제를 버전 관리 기능으로 해결했다고 말하지 않는다.
- 산업 용어는 한 문장으로만 풀고, 사용자의 과업과 내 판단을 설명한다.
- 질문에 먼저 답하고 사례를 붙인다. 한 답변에 세 사례를 모두 넣지 않는다.

# 포트폴리오 PT 발표 대본

## 1. 발표 운영 방식

기본 구성은 **통합 플랫폼 + TBM**입니다. 실제 배포 사례에서 내가 결정한 내용을 보여주는 조합입니다. ERP는 B2B SaaS·운영 도구·데이터 UX 공고에서 확장 사례로 추가합니다. 산업 자체에 관심을 고정시키지 않도록 제목 다음에는 “탐색”, “기록”, “확인 상태”, “자료 조회”라는 보편적인 과업으로 설명합니다.

이 문서는 발표 대본이며 새로운 슬라이드 파일은 아닙니다. 현재 PDF를 보며 발표할 때는 아래 페이지를 사용합니다. 기업에서 별도 발표 덱, 사례 수 또는 특정 양식을 요청하면 그 안내가 우선입니다. 웹만 있는 반려동물·반응형 사례는 별도 탭에 준비합니다.

| 발표 시간 | 추천 범위 | 운영 |
|---|---|---|
| 3분 | 자기소개 + 플랫폼의 핵심 결정 | 4·8·10쪽, 나열 금지 |
| 5분 | 플랫폼 2분 + TBM 2분 + 도입/마무리 | 아래 5분 압축 대본 |
| 10분 | 플랫폼 4분 + TBM 4분 + 도입/마무리 | 기본 대본, 리허설로 속도 조정 |

> 마지막은 공통 UI 기준과 웹 가이드입니다. 범위를 정확히 말씀드리면 전사 디자인 시스템 운영 사례가 아니라, 공통 컬러와 일부 입력·검색 UI를 정리하고 재사용한 사례입니다.
>
> 컬러 값은 SCSS 변수로 정의하고 웹 가이드에서 같은 기준을 참고하도록 했습니다. 입력 UI에서는 읽기 전용과 편집 가능한 상태를, 검색에서는 기본·포커스·입력 중·비활성을 구분했습니다. 공통 기준을 유지하되 화면의 맥락에 따라 입력 영역의 크기와 배치는 조정했습니다.
>
> 컬러와 일부 UI 요소는 디자이너의 디자인·프론트 작업에서 재사용했습니다. 다만 조직 전체의 도입률이나 제작 시간 감소는 측정하지 않았습니다. 더 확장한다면 새 컴포넌트 수를 늘리기보다 실제로 중복되는 요소와 상태를 먼저 확인하고, 사용 기준과 예외, 변경 시 영향을 받는 화면을 함께 관리하겠습니다.
>
> 저는 공통 기준을 정하는 것과 개별 화면에 맞게 적용하는 것을 함께 다룬 경험으로 이 사례를 설명하고 싶습니다.

## 4. 5분 압축 대본

### 시작 / 25초

> 안녕하세요. 업무의 정보와 상태를 사용자가 이해하고 처리할 수 있는 화면으로 만드는 이한울입니다. 웹디자인·퍼블리싱에서 B2B 서비스 설계로 경험을 넓혔습니다. 배포 경험이 있는 두 사례에서 제가 한 판단과 결과를 말씀드리겠습니다.

### 플랫폼 / 2분 / 4·8·10쪽

> 통합 플랫폼에서는 초기 메뉴에서 기능의 업무 분야를 구분하기 어려웠습니다. 기획자가 현장 설명과 사업 관리로 나누는 방향을 제안했고, 저는 이를 지도 위의 메뉴 UI로 구체화하고 퍼블리싱했습니다.
>
> 핵심 결정은 메뉴의 배경 표현입니다. 흰색안은 경계가 분명하지만 지도와 분리돼 보였고, 검정안은 메뉴 존재감이 강했습니다. 저는 메뉴 구분과 지도 배경의 연속성을 함께 고려해 반투명 검정안을 선택했습니다. 또 위치 확인, 업무 메뉴 선택, 자료 유형 선택의 역할을 나눴습니다.
>
> 플랫폼은 배포 후 실제 사용됐고 내부 동료에게 메뉴 구분이 명확하다는 의견을 받았습니다. 현장 사용자 테스트나 클릭 수 감소를 측정한 것은 아닙니다. 다음에는 같은 자료 찾기 과업으로 첫 선택과 완료 시간을 확인하겠습니다.

### TBM / 2분 / 11·13·14·15쪽

> TBM은 작업 전 점검 내용을 기록·확인·보관하는 서비스입니다. 저는 모바일 일지와 서명 화면을 기획·디자인하고 웹 UI에 참여했습니다.
>
> 일지에서는 작성일과 출역 인원으로 작성 맥락을 먼저 확인하고, 담당자·현장 책임자의 확인 상태와 작성 버튼을 구분했습니다. 서명에서는 입력·변경과 저장 완료를 분리했습니다. 서명 정보의 저장이 일지 전체의 제출 완료로 오해되지 않도록 완료 범위를 정확히 다루는 것이 중요합니다.
>
> 이후 사이트 안에서 파일을 보고 싶다는 요청에 따라 PDF·HWP 열람 UI의 디자인과 퍼블리싱도 추가했습니다. 파일 처리 엔진 개발은 제 범위가 아닙니다. 서비스는 배포 후 사용됐고 사용자 의견은 개발자를 통해 전달받았습니다. 공개 화면은 설명용 재구성이며, 업무 시간 감소를 측정한 자료는 없습니다.

### 마무리 / 35초

> 두 사례에서 저는 업무의 맥락과 다음 행동을 구분하고 구현 기준으로 구체화했습니다. 새로운 산업에서도 기록·조회·상태가 복잡한 문제를 정리하는 데 기여할 수 있습니다. 앞으로는 설계 초기에 성공 기준과 확인 방법을 정하고, 실제 사용자 피드백과 결과를 다음 개선으로 연결하는 책임을 넓히고 싶습니다. 감사합니다.

5분 대본은 발화량에 따라 4분대로 끝날 수 있습니다. 남는 시간은 화면의 핵심 영역을 가리키며 설명하되 새 프로젝트를 급히 추가하지 않습니다.

# 직무·프로젝트 심층 문답 60개

답변은 기본적으로 30–60초 분량으로 확장해 말합니다. 먼저 굵은 질문에 직접 답하고, 현재 화면 하나를 근거로 붙이세요. “앞으로 하겠습니다”, “다시 한다면”은 실제 수행 이력이 아닙니다. 자료에 없는 기술·정책의 동작은 화면만 보고 확정하지 않습니다.

## A. 대표 프로젝트와 기여 범위

### Q01. 가장 자신 있는 프로젝트는 무엇인가요?

> 통합 관리 플랫폼입니다. 기획자가 제안한 업무별 메뉴 구분을 지도 위에서 실제로 읽히는 UI로 구체화했습니다. 메뉴 배경 세 안을 비교하고, 메뉴 경계와 지도 연속성을 함께 고려한 반투명 검정안을 선택해 퍼블리싱했습니다. 배포 후 사용까지 이어졌고, 제 판단과 구현 범위를 가장 구체적으로 설명할 수 있는 사례입니다.

꼬리: “왜 회사의 성과가 아니라 본인의 성과인가요?” → 제품 전체의 성공을 제 성과로 주장하는 것이 아니라, 메뉴 표현의 선택과 지도 탐색 UI·퍼블리싱을 제 기여로 설명합니다.

### Q02. 기획자가 메뉴를 나눴다면 UX는 누가 한 건가요?

> 업무 분야를 나누자는 방향은 기획자가 제안했습니다. 저는 사용자가 그 구분을 화면에서 알아볼 수 있게 메뉴 배경과 선택 상태, 지도와 자료 영역의 관계를 구체화했습니다. UX는 한 사람이 독점하는 역할이라기보다 여러 직군의 판단이 이어지는 과정이라고 생각합니다. 그 과정에서 제 몫은 UI 결정과 구현이었습니다.

금지: “정보 구조 전체를 혼자 새로 설계했습니다.”

### Q03. 플랫폼 문제를 어떻게 발견했나요?

> 프로젝트를 인계받으면서 여러 파일과 기존 프로그램을 살펴봤고, 초기 메뉴에서 기능의 업무 분야가 잘 구분되지 않는 문제를 확인했습니다. 이 자료 검토와 협의가 현재 설명할 수 있는 근거입니다. 정식 사용자 인터뷰나 현장 관찰 연구를 진행한 것처럼 설명하지는 않습니다.

추가로 실제 인계 자료나 회의 기록을 갖고 있다면 공개 가능한 범위 안에서 어떤 문서였는지 본인 기억을 보완합니다.

### Q04. 왜 반투명 검정인가요? 그냥 취향 아닌가요?

> 지도 위 메뉴이기 때문에 메뉴 영역은 구분되면서 지도 맥락도 이어져야 한다는 두 기준으로 비교했습니다. 흰색은 지도와 분리돼 보이고 검정은 존재감이 강했습니다. 두 기준을 절충해 반투명 검정을 선택했습니다. 다만 사용자 실험으로 우수성을 입증한 결정은 아니어서, 지금이라면 다양한 지도 배경에서 가독성과 메뉴 선택 과업을 검증하겠습니다.

꼬리: “최적안이라고 확신하나요?” → 당시 기준에 맞춘 선택이며 모든 배경에서 최적이라는 뜻은 아닙니다.

### Q05. 반투명 UI는 접근성 문제가 없나요?

> 문제가 없다고 단정할 수 없습니다. 배경이 달라지면 텍스트와 선택 상태의 대비도 달라지기 때문입니다. 다시 확인한다면 밝고 복잡한 지도 배경, 확대 수준별로 메뉴의 대비와 포커스 표시를 보고, 충분하지 않으면 배경 불투명도나 별도 표면을 조정하겠습니다. 현재 자료는 접근성 적합성 검사 결과를 제시한 것은 아닙니다.

### Q06. 플랫폼의 전후 성과는 무엇인가요?

> 확인된 결과는 메뉴·지도 UI를 설계하고 퍼블리싱한 플랫폼이 배포 후 실제 사용됐다는 점입니다. 내부 동료에게 메뉴 구분이 명확하다는 의견도 받았습니다. 탐색 시간·클릭 수 변화나 분산된 자료의 최종본 문제가 해결됐는지는 측정하지 않았습니다. 따라서 산출물, 사용 사실, 정성 의견을 나눠 설명하고 있습니다.

### Q07. 왜 직접 사용자에게 물어보지 않았나요?

> 당시 제가 확보한 근거는 자료 검토와 협업, 내부 의견과 개발자를 통해 전달된 의견이었습니다. 직접 사용자 검증이 부족했던 점은 한계입니다. 다음에는 기획 초기부터 사용자 접점과 확인 일정을 요청하고, 어렵다면 담당자 동석 과업 관찰이나 원격 프로토타입 테스트처럼 가능한 방법부터 확보하겠습니다.

자료에 없는 “보안 때문에 절대로 만날 수 없었다” 같은 이유를 만들어 붙이지 않습니다.

### Q08. 클릭 수가 줄어드는 게 항상 좋은 UX인가요?

> 아닙니다. 확인이 필요한 업무에서는 단계를 줄이면 오히려 실수 위험이 커질 수 있습니다. 목적은 불필요한 탐색을 줄이되 중요한 결정을 이해하고 실행하도록 하는 것입니다. 완료율과 소요 시간에 더해 오선택·되돌아감·확인 누락을 함께 보겠습니다.

### Q09. TBM에서 직접 맡은 범위를 정확히 말해보세요.

> 모바일 일지·서명 화면의 기획과 디자인, 웹 UI에 참여했고, 이후 추가된 사이트 내 파일 열람 기능은 디자인과 퍼블리싱을 맡았습니다. 서비스 전체의 기획과 백엔드, 문서 변환 엔진까지 제가 담당한 것은 아닙니다. 모바일 작성·확인과 웹 자료 열람의 UI를 중심으로 설명할 수 있습니다.

### Q10. 종이 양식을 그대로 화면으로 옮긴 것 아닌가요?

> 기존 양식의 항목을 이해하는 것은 출발점이지만, 화면에서는 작성 맥락·확인 상태·다음 행동의 순서를 구분했습니다. 작성일과 출역 인원을 먼저 확인하고 담당자별 확인 상태와 작성 진입을 나눴습니다. 다만 모든 항목의 필요성을 사용자 연구로 재검증한 것은 아니므로, 다음에는 실제 작성 순서와 중단 지점도 관찰하고 싶습니다.

### Q11. 서명 저장 완료가 왜 중요한가요?

> 입력한 서명이 화면에 보인다는 사실과 저장이 끝났다는 사실은 다르기 때문입니다. 입력·변경 화면 뒤에 저장 결과를 표시해 사용자가 작업 상태를 알 수 있도록 했습니다. 그리고 서명 저장은 마이페이지의 서명 정보에 대한 결과이므로, 일지 제출·승인이 끝난 상태와 구분해서 표현해야 합니다.

### Q12. 저장 실패·오프라인·중복 제출은 어떻게 처리했나요?

> 현재 포트폴리오로 설명할 수 있는 것은 입력·변경과 저장 완료 화면입니다. 오프라인이나 중복 제출 처리를 모두 구현·검증했다고 말할 근거는 없습니다. 앞으로 설계한다면 입력 보존 여부, 재시도, 요청 중 상태, 성공 응답과 중복 처리 기준을 개발자와 합의하고 사용자가 현재 상태를 알 수 있게 하겠습니다.

**[앞으로의 제안]**: 진행 중 / 성공 / 실패 / 결과 불명확을 구분합니다. 서버 멱등성 등은 개발 협의 항목이며 실제 구현 이력으로 말하지 않습니다.

### Q13. 사용자 요청을 받으면 무조건 추가하나요?

> 요청을 그대로 화면 목록으로 바꾸기 전에 누가, 어떤 상황에서, 얼마나 자주 겪는 문제인지 확인해야 한다고 생각합니다. TBM에서는 사이트 안에서 파일을 보고 싶다는 담당자 요청에 따라 열람 UI를 추가했습니다. 당시 실제 이용 빈도나 시간 변화까지 측정하지는 못했습니다. 다음에는 대체 방법과 작업 영향, 비용을 비교해 우선순위의 근거를 남기겠습니다.

### Q14. HWP 파일 열람을 직접 구현했다는 건가요?

> 제가 담당한 것은 파일 목록과 문서 열람 UI의 디자인·퍼블리싱입니다. HWP를 변환하거나 렌더링하는 기술 자체를 개발한 것은 아닙니다. 로딩·열람 불가·권한 상태를 어떤 방식으로 알릴지는 개발과 정책을 확인해 설계해야 하는 부분입니다.

### Q15. 개발자를 통한 의견도 사용자 리서치인가요?

> 사용자와 관련된 단서는 될 수 있지만 직접 수집한 리서치 결과와 동일하게 취급하지 않습니다. 어떤 사용자에게 어떤 상황에서 나온 의견인지, 요약 과정에서 빠진 맥락이 있는지 확인할 필요가 있습니다. 다음에는 전달자의 해석과 실제 사용자 발언·행동을 분리해 기록하고 직접 확인할 질문으로 연결하겠습니다.

### Q16. ERP는 왜 미사용됐나요? 본인의 잘못 아닌가요?

> 확인되는 사실은 최종 제공 형식이 PDF로 바뀌어 웹 설계안이 사용되지 않았다는 것입니다. 변경의 모든 조직적 이유나 책임을 자료만으로 단정하지 않겠습니다. 제가 가져갈 개선점은 화면 설계 전에 직접 조회가 필요한 사용자와 보고서를 받을 사용자, 전달 형식을 더 일찍 합의하는 것입니다.

꼬리: “어떤 시점에 누가 결정했나요?” → **[본인 사실 입력]** 실제 기억과 기록으로 답합니다. 결정권자·이유·일정의 빈칸을 추측으로 채우지 않습니다.

### Q17. 미사용 프로젝트를 왜 포트폴리오에 넣었나요?

> 조회 조건에서 요약과 상세로 이어지는 정보 위계와 상태 표현, 퍼블리싱 역량을 보여주기 위해 넣었습니다. 성공적인 출시 사례로 소개한 것은 아닙니다. 최종 미사용 결과와 산출물 형식 합의의 중요성을 함께 설명할 수 있는 사례라고 생각합니다.

### Q18. 전사·프로젝트·개인은 권한 체계인가요?

> 이 사례에서 설명한 것은 어떤 범위의 정보를 조회하는지에 대한 구분입니다. 이 메뉴만으로 접근 권한까지 설계했다고 주장하지 않습니다. 실제 제품이라면 조회 범위와 별개로 서버 권한, 데이터 노출 범위, 권한 없음 상태를 확인해야 합니다.

### Q19. 대시보드에서 어떤 정보부터 보여주나요?

> 사용자가 지금 내릴 결정에서 출발합니다. 이 사례에서는 조회 조건을 먼저 정하고, 주요 수치와 현황 요약, 프로젝트·인원별 상세를 이어 보도록 구성했습니다. 정보의 양을 줄이는 것만이 목표는 아닙니다. 조건과 숫자의 관계, 요약과 상세의 연결이 읽혀야 합니다.

꼬리: “어떤 숫자가 제일 중요한지 누가 정했나요?” → 당시 요구사항과 협의에서 확인한 사실만 말하고, 자료에 없는 의사결정 권한은 주장하지 않습니다.

### Q20. 합계나 초과 근무를 왜 색으로 강조했나요?

> 기본 정보와 구분해서 확인할 수 있도록 선택 상태·합계·초과 상태의 강조를 정리했습니다. 색만으로 의미를 전달하면 놓칠 수 있어 숫자와 문구도 함께 이해돼야 한다고 생각합니다. 화면의 9시간/기준 8시간은 상태를 설명하는 예시이지 실제 초과 근무 감소 성과는 아닙니다.

### Q21. 디자인 시스템을 어디까지 만들었나요?

> 공통 컬러를 SCSS 변수로 관리하고, 입력·검색 상태와 배치를 웹 가이드로 정리했습니다. 컬러와 일부 UI를 디자이너의 디자인·프론트 작업에서 재사용했습니다. 전사 컴포넌트 라이브러리의 버전 관리나 조직 전체의 도입·운영을 주도한 경험으로 확대해 설명하지는 않습니다.

### Q22. 토큰과 스타일 가이드, 컴포넌트의 차이는요?

> 토큰은 색·간격 같은 반복되는 디자인 결정을 이름으로 관리하는 단위이고, 스타일 가이드는 그 기준과 사용법을 설명합니다. 컴포넌트는 여러 속성과 상태를 가진 재사용 UI 단위입니다. 저는 이 중 공통 컬러 변수와 입력·검색 상태 기준을 정리하고 적용한 경험이 있습니다.

### Q23. 읽기 전용과 비활성은 어떻게 다른가요?

> 읽기 전용은 정보를 확인하되 수정할 수 없는 상태, 비활성은 현재 조건에서 기능을 사용할 수 없는 상태로 구분합니다. 시각적 차이만으로 끝내지 않고 왜 사용할 수 없는지와 대안이 필요한지 살펴야 합니다. 실제 HTML에서는 요소와 속성에 따라 포커스·폼 전송 등의 동작이 다르므로 구현 의미도 함께 확인합니다.

### Q24. 가이드를 만들면 모두가 사용하는 건가요?

> 그렇지는 않습니다. 사용 상황에 맞고 찾기 쉬우며 구현과도 맞아야 계속 쓰게 됩니다. 제 사례는 일부 재사용까지 확인한 범위입니다. 확장한다면 자주 쓰는 요소부터 사용 기준·예외·변경 이력을 관리하고, 실제 채택과 유지 비용을 보겠습니다.

### Q25. 인트라넷은 실제 서비스됐나요?

> 아닙니다. 디자이너 팀에서 회의실 예약·근태 신청 화면의 기획·UI·퍼블리싱에 참여했고, 팀 내부에서 설계·구현을 확인한 미배포 프로젝트입니다. 실제 직원의 업무 처리 시간이 줄었다는 성과로 설명하지 않습니다.

### Q26. 회의실 예약에서 무엇을 검증할 건가요?

> **[앞으로의 제안]** 원하는 날짜와 시간에 가능한 회의실을 찾아 예약하는 과업을 보겠습니다. 공간 현황을 이해하는지, 날짜와 시작·종료 시간을 잘 입력하는지, 중복 예약이나 마감 직전 충돌을 어떻게 이해하는지 확인하겠습니다. 최종 예약 가능 여부는 서버 응답을 기준으로 표시해야 한다고 생각합니다.

### Q27. 칸반은 기존 제품과 무엇이 다른가요?

> 현재 단계에서 검증된 시장 차별점을 주장하지는 않습니다. 이미지와 제목을 함께 보는 보드 UI를 설계하고, AI 도움으로 카드 이동과 작업 생성을 구현한 개인 프로토타입입니다. 어떤 사용자에게 기존 도구보다 나은지는 이후 검증할 문제입니다.

### Q28. 칸반에서 가장 먼저 바꿀 것은요?

> 작업 분야와 진행 상태가 같은 수준의 컬럼으로 섞인 부분입니다. 분야는 카드의 분류 속성으로, 진행 상태는 보드 컬럼으로 나누는 안을 먼저 비교하겠습니다. 그다음 사용자가 작업을 만들고 상태를 바꾸는 과업을 실제로 수행하며 구조를 이해하는지 확인하겠습니다.

### Q29. 반려동물 앱의 습관 형성 효과를 어떻게 알았나요?

> 현재는 효과를 검증한 단계가 아닙니다. 진행률·빠른 기록·오늘의 일정을 우선 배치하고, 업적과 리포트로 기록을 다시 확인할 계기를 설계한 개인 작업입니다. 실제 사용이 이어지는지는 반복 사용 관찰과 기록 완료·재방문 지표로 확인해야 합니다.

### Q30. PSC에서는 기술을 어디까지 했나요?

> 센서 연결과 측정 상태, 거더별 결과를 확인하는 정보 구조와 웹·앱 UI, 퍼블리싱을 담당했습니다. 센서 하드웨어나 분석 알고리즘을 개발하거나 측정 정확도를 개선한 성과로 설명하지는 않습니다. 이 경험은 기술이 생성한 데이터를 사람이 이해할 수 있게 만드는 일로 다른 산업에 연결할 수 있습니다.

## B. UX와 제품 판단

### Q31. UX 디자이너와 프로덕트 디자이너의 차이는 무엇인가요?

> 회사마다 역할은 다릅니다. 제 기준으로는 사용자의 경험을 설계하는 것에 더해 사업 목표, 우선순위, 출시와 결과 확인까지 어느 범위를 책임지는지가 중요합니다. 저는 정보 구조·UI·구현 협업이 강점이고, 성장 지표를 반복 검증하는 경험은 더 쌓아야 합니다. 직함보다 해당 팀이 기대하는 책임 범위를 확인하고 싶습니다.

### Q32. 디자인 프로세스를 설명해주세요.

> 실제 해온 방식은 업무 자료와 요구사항을 이해하고, 정보 위계와 흐름을 정리한 뒤 UI와 구현 기준을 구체화하는 것입니다. 기획·개발과 조율하고 퍼블리싱까지 연결했습니다. 앞으로는 이 시작 단계에 사용자 근거와 성공 기준을 더 분명히 넣고, 출시 후 과업 결과를 확인해 다음 수정으로 이어가겠습니다.

금지: 수행하지 않은 정식 인터뷰·정량 분석·A/B 테스트를 매번 해 온 표준 프로세스처럼 나열하기.

### Q33. 사용자의 요구와 진짜 문제는 어떻게 구분하나요?

> 요구한 기능이 없어서 어떤 일을 못 하는지, 지금은 어떻게 해결하는지, 얼마나 자주 생기며 잘못되면 어떤 비용이 드는지 확인하겠습니다. 예를 들어 “다운로드 버튼을 크게 해달라”는 요구라면 파일을 못 찾는 문제인지, 버튼 인지 문제인지, 반복 다운로드 자체가 문제인지 나눠 봐야 합니다.

### Q34. 데이터가 없으면 어떻게 판단하나요?

> 먼저 확인된 사실과 가정을 구분합니다. 기존 화면·업무 자료·문의 기록과 담당자 설명으로 문제를 좁히고, 위험이 큰 가정부터 작은 프로토타입이나 과업 관찰로 확인하겠습니다. 데이터가 없다는 이유로 결정을 멈추기보다, 결정의 불확실성과 되돌릴 수 있는 범위를 명확히 하겠습니다.

### Q35. 리서치를 한다면 누구에게 무엇을 물을 건가요?

> **[앞으로의 제안]** 사용자 직함만이 아니라 과업 빈도·숙련도·역할이 다른 사람을 고르겠습니다. 최근 실제로 업무를 처리한 사례를 보여달라고 하고 시작 계기, 찾는 정보, 우회 방법, 실수와 복구를 살피겠습니다. “이 기능 좋으세요?”보다 “마지막으로 처리한 과정을 설명해 주세요”처럼 행동을 묻겠습니다.

### Q36. 사용성 테스트는 어떻게 설계하나요?

> **[앞으로의 제안]** 핵심 가설과 과업을 정하고, 답을 유도하지 않는 상황을 제시하겠습니다. 예를 들어 “A 프로젝트의 지난달 투입 현황을 확인해 주세요”입니다. 도움 없이 완료했는지, 어디서 망설이거나 잘못 선택했는지와 소요 시간을 기록하고, 반복되는 문제의 영향과 빈도로 수정 순서를 정하겠습니다. 인원 수만으로 충분한 검증이라고 단정하지는 않겠습니다.

### Q37. 인터뷰와 사용성 테스트의 차이는요?

> 인터뷰는 사용자의 맥락과 목표·기존 행동을 이해하는 데, 사용성 테스트는 특정 설계에서 과업을 수행할 수 있는지 확인하는 데 적합합니다. 사용자가 말한 선호와 실제 수행은 다를 수 있어 질문과 관찰을 구분해야 합니다.

### Q38. UX 성과 지표를 정해보세요.

> 목표 과업에 따라 정하겠습니다. 자료 탐색이면 목표 자료 도달 성공률과 시간, 기록이면 제출 완료율과 수정·누락 비율, 예약이면 예약 성공과 충돌 해결을 보겠습니다. 화면 클릭 증가를 곧바로 성과로 보지 않고 실제 과업과 연결하겠습니다. 이는 다음 프로젝트의 측정 계획이며 과거 실적 수치는 아닙니다.

### Q39. 완료율은 어떻게 정의하나요?

> 분모와 분자의 이벤트, 사용자를 포함하는 기준, 기간을 먼저 합의하겠습니다. 예를 들어 작성 시작 대비 서버에서 저장 성공이 확인된 제출의 비율로 정의할 수 있습니다. 자동 저장·중복 시도·테스트 계정·재시도 같은 예외를 처리하지 않으면 수치를 잘못 읽을 수 있습니다.

### Q40. 지표가 좋아졌으면 디자인 때문인가요?

> 바로 인과관계를 말할 수는 없습니다. 사용자 구성, 계절성, 기능·정책 변경이 함께 영향을 줄 수 있습니다. 가능한 경우 비교군이나 실험을 설계하고, 어려우면 같은 과업과 조건에서 관찰한 전후 변화라는 수준으로 해석하겠습니다. 표본이 적을 때는 성공/실패의 개별 이유도 함께 봐야 합니다.

### Q41. A/B 테스트를 언제 쓰겠습니까?

> 비교할 가설이 명확하고 필요한 사용자 수·시간을 확보할 수 있으며 실험이 사용자에게 허용 가능한 위험일 때 검토하겠습니다. 소수의 업무 사용자가 반복 이용하는 제품에서 무조건 A/B 테스트가 답은 아닙니다. 과업 테스트나 단계적 배포가 더 적합할 수 있습니다. 현재 대표 사례에서 직접 A/B 실험을 운영한 결과는 없습니다.

### Q42. 기능 우선순위는 어떻게 정하나요?

> 사용자 문제의 심각도와 빈도, 사업 목표와 연결성, 개발 비용·의존성, 현재 근거의 확실성을 비교하겠습니다. 우선순위 프레임워크는 대화를 돕는 도구로 사용하되 근거 없는 점수를 정밀한 숫자로 포장하지 않겠습니다. 되돌리기 어렵거나 오류 비용이 큰 항목도 함께 고려합니다.

### Q43. 일정이 절반으로 줄면 무엇을 포기하나요?

> 핵심 과업의 시작과 완료를 연결하는 흐름, 중요한 상태와 오류 안내를 먼저 남기겠습니다. 드물게 쓰는 설정, 추가 시각 효과, 부가적인 탐색 기능은 범위를 줄일 수 있습니다. 다만 어떤 이용자가 영향을 받는지와 다음에 보완할 항목을 합의하고 기록하겠습니다.

### Q44. 비즈니스와 사용자 요구가 충돌하면요?

> 사용자의 어려움과 사업이 원하는 결과를 구체적인 행동으로 바꿔 비교하겠습니다. 단기 전환을 높여도 오해·취소·문의가 늘 수 있으므로 후행 결과와 보호 지표도 함께 보겠습니다. 충돌을 취향 대립으로 만들기보다, 선택의 비용과 검증 방법을 제시하겠습니다.

### Q45. B2B와 B2C의 차이를 어떻게 보나요?

> B2B에서는 역할·권한·반복 과업·데이터 정확성과 기존 업무 방식이 중요하게 작용하는 경우가 많고, 구매자와 실사용자가 다를 수 있습니다. B2C에서는 첫 사용과 가치 이해, 동기와 재방문이 중요할 수 있습니다. 다만 이를 절대적인 구분으로 보지 않고 실제 사용자와 과업 빈도·실패 비용을 확인하겠습니다.

## C. UI·개발 협업·경력 수준

### Q46. 좋은 UI를 판단하는 기준은 무엇인가요?

> 핵심 과업과 정보 위계가 읽히는지, 현재 상태와 다음 행동이 분명한지, 타입·간격·정렬·색이 일관되는지, 예외와 다른 화면 크기에서도 동작하는지를 보겠습니다. 플랫폼 메뉴처럼 시각적 선택을 실제 사용 맥락과 연결해서 설명할 수 있어야 한다고 생각합니다.

### Q47. 테이블이 복잡하면 어떻게 줄이나요?

> 열을 무조건 없애기보다 어떤 비교와 결정을 해야 하는지 먼저 보겠습니다. 핵심 열 우선순위와 상세 분리, 정렬·필터의 필요성을 정하고, 단위·기간·합계 기준을 일관되게 표시하겠습니다. 가로 이동·고정 열·작은 화면의 대안은 실제 데이터 길이와 사용자 과업으로 비교하겠습니다.

### Q48. 반응형은 화면을 줄이는 일인가요?

> 아닙니다. 화면 크기가 달라져도 중요한 정보와 탐색 순서를 유지하도록 재배치하는 일입니다. 테스콤에서는 제품·솔루션의 진입점과 목록 배치를 다뤘습니다. 제목 길이·다국어·이미지 비율·긴 표·터치 조작처럼 실제 콘텐츠 조건으로 확인하는 것이 중요합니다. 문의 증가 같은 측정 성과는 없습니다.

### Q49. 접근성을 어떻게 고려하나요?

> 색상 외의 상태 단서, 텍스트 대비, 키보드 접근과 포커스, 적절한 레이블과 읽는 순서, 입력 오류 안내 등을 확인하겠습니다. 실제 구현까지 포함해 검사해야 하며, 시각적 시안만으로 준수를 주장하지 않겠습니다. 회사가 요구하는 표준과 지원 환경을 먼저 확인하겠습니다.

### Q50. Figma는 어느 정도 하나요?

> 화면 설계와 개발 협의를 위한 디자인 도구로 사용합니다. 실제로 설명할 수 있는 기능과 파일을 기준으로 말씀드리겠습니다. 오토 레이아웃·컴포넌트·변형·변수·프로토타입은 각각 **[본인이 실제 활용한 범위]**를 예시 파일로 확인해 두겠습니다. 포트폴리오 이미지가 있다는 이유만으로 모든 고급 기능을 쓴 것처럼 말하지 않겠습니다.

연습: 실제 파일 하나를 열고 구조·재사용·네이밍·상태·핸드오프를 3분 안에 설명합니다. 이 다섯 항목은 증빙 준비 항목이며 현재 사용 여부를 단정한 목록이 아닙니다.

### Q51. 개발자가 구현이 어렵다고 하면요?

> 어려운 이유가 일정·기술·데이터·정책 중 무엇인지 먼저 확인하겠습니다. 사용자가 얻어야 할 결과는 유지하면서 동작이나 표현을 단순화하는 대안을 비교하고, 핵심 상태를 어느 범위까지 구현할지 합의하겠습니다. 실제 협업에서는 퍼블리싱 경험을 바탕으로 간격·강조·상태 같은 구현 기준을 구체화했습니다.

구체적 갈등 일화를 요구받으면 **[본인 사실 입력]** 실제 사례를 사용합니다.

### Q52. 디자인 QA는 무엇을 보나요?

> 시안과 픽셀을 맞추는 것에 더해 핵심 과업이 시작부터 완료까지 되는지 보겠습니다. 기본·로딩·빈 상태·오류·권한·완료, 긴 데이터·다른 해상도·입력과 키보드 흐름을 확인하겠습니다. 디자인과 다른 점을 모두 같은 수준으로 요청하지 않고 사용 차단·오인 위험·시각적 불일치로 나눠 우선순위를 제안하겠습니다.

이 전체 절차를 과거 모든 프로젝트에서 수행했다고 말하지 않습니다.

### Q53. 퍼블리싱이 디자이너에게 어떤 도움이 되나요?

> 간격과 레이아웃, 반응형, 입력 상태를 실제 화면으로 구체화하면서 시안과 구현의 해석 차이를 확인하는 데 도움이 됩니다. 개발자와 구현 제약을 논의할 수 있는 기반도 됩니다. 다만 퍼블리싱 역량이 사용자 문제 정의나 제품 성과를 대신한다고 생각하지는 않습니다.

### Q54. JavaScript·Git·React 범위를 알려주세요.

> HTML·CSS·SCSS와 JavaScript, Git은 작업에 사용하고 React는 학습 중입니다. 실제 JavaScript로 만든 동작과 Git에서 사용하는 작업은 코드·이력으로 설명하겠습니다. React 실무 서비스를 독립적으로 설계·배포한 경력으로 말씀드리지는 않습니다. 개인 칸반은 AI 보조 구현이라는 점을 구분합니다.

추가 준비: 본인이 직접 설명할 수 있는 JS 동작 두 개, Git 충돌/브랜치 경험의 실제 범위, React에서 지금 구현 가능한 작은 화면 하나를 적습니다.

### Q55. AI를 썼는데 본인 실력이라고 할 수 있나요?

> 무엇을 만들지 정한 UI와 흐름, AI가 보조한 코드, 제가 확인한 결과를 분리해서 설명해야 한다고 생각합니다. 칸반에서는 보드 UI를 설계하고 AI 도움으로 카드 이동·작업 생성을 구현했습니다. 동작이 만들어졌다는 사실과 사용자에게 유용하다는 검증도 구분하고 있습니다. 사용자 평가는 아직 하지 않았습니다.

“AI 코드의 모든 줄을 이해한다”는 답변은 실제로 설명할 수 있을 때만 사용합니다.

### Q56. 6~7년 차에게 기대되는 주도성은 무엇이라고 보나요?

> 요청된 화면을 처리하는 데서 끝내지 않고, 해결할 문제와 범위를 명확히 하고 의존성과 위험을 미리 드러내는 것이라고 생각합니다. 제 경험에서는 복잡한 업무를 UI·구현 기준으로 구체화한 부분이 강점입니다. 더 보완할 점은 초기에 성공 기준과 사용자 확인 경로까지 설계해 결과 책임을 넓히는 것입니다.

### Q57. 다른 시니어 지원자보다 어떤 강점이 있나요?

> 제품 성장 실험을 많이 해 온 지원자와 같은 강점을 내세우기보다, 복잡한 데이터·기록·조회 흐름을 정리하고 UI·퍼블리싱과 개발 협업까지 이어온 경험을 제 강점으로 말씀드리고 싶습니다. 팀이 당장 필요한 문제가 정보 구조와 업무 화면의 구체화라면 빠르게 기여할 수 있습니다.

### Q58. 리딩·멘토링·채용 경험이 있나요?

> 현재 포트폴리오에서는 공식 조직 리딩·채용·평가를 수행한 근거를 제시하지 않았습니다. 개인 작업의 책임과 팀의 인사 관리 경험은 구분해서 말씀드리겠습니다. 실제 동료 지원이나 리뷰 경험이 있다면 **[본인 사실 입력]** 범위와 결과를 설명하겠습니다. 경험이 없다면 있다고 만들지 않겠습니다.

지원 판단: 인사 관리가 핵심인 Lead/Manager와 Senior IC의 기대 역할을 구분합니다.

### Q59. 입사 후 첫 90일을 어떻게 보내겠습니까?

> 첫 30일은 제품의 사용자·핵심 과업·정책·데이터·협업 구조를 이해하겠습니다. 다음 30일은 팀이 중요하게 보는 문제 하나를 골라 근거와 성공 기준, 개선안을 합의하고 작은 범위로 검증하겠습니다. 이후에는 출시 또는 검증 결과를 정리해 다음 개선을 제안하겠습니다. 구체 일정과 목표는 팀 상황에 맞춰 조정하겠습니다.

### Q60. 지금 본인의 가장 큰 부족함은 무엇인가요?

> 정량 지표와 직접 사용자 검증을 통해 개선을 반복한 경험의 깊이입니다. 이를 감추기보다 제가 확인한 결과의 범위를 명확하게 말하고 있습니다. 다음 작업에서는 지표를 나중에 붙이는 대신, 문제를 정할 때 핵심 과업과 관찰할 행동, 데이터 수집 방법을 함께 정하는 방식으로 보완하고 싶습니다.

“환경이 안 좋아서 못 했다”로 끝내지 말고, 자신의 다음 행동까지 설명합니다.

## 면접관의 질문이 깊어질 때 공통 구조

1. “당시 확인한 사실은 …입니다.”
2. “제가 직접 한 선택은 …입니다.”
3. “다른 선택지와 비교한 기준은 …입니다.”
4. “확인하지 못한 부분은 …입니다.”
5. “지금 다시 한다면 …을 먼저 확인하겠습니다.”

모든 답에 다섯 문장을 기계적으로 넣지 않아도 됩니다. 이 구분을 유지하면 압박 질문에서도 실제 경험을 지킬 수 있습니다.

# 채용 절차·컬처핏·역량검사 실전 준비

## 1. 채용 단계별로 무엇을 보여줄 것인가

모든 회사에 모든 단계가 있는 것은 아닙니다. 실제 초대 메일의 안내를 우선합니다. 아래는 여러 전형에 대비하기 위한 구성입니다.

| 단계 | 나에게 확인될 질문 | 준비 결과물 |
|---|---|---|
| 서류 | 어떤 문제를 풀 수 있는가, 요구 연차와 맞는가 | 경력 요약·실제 기간·역할, 대표 사례 2개 |
| 리크루터/전화 | 이직 이유·업종 전환·지원 동기·입사 일정 | 30초 소개, 회사별 네 문장 |
| 포트폴리오 PT | 문제·기여·선택 근거·결과가 연결되는가 | 플랫폼+TBM 대본, 근거 화면 |
| 실무 심층 | 데이터·상태·예외·협업까지 생각하는가 | 문답 60개, 본인 사실 6개 |
| 사전 과제 | 모호한 문제를 어디까지 좁혀 설계하는가 | 문제 정의·가정·핵심 흐름·검증 계획 |
| 라이브 과제 | 질문·우선순위·협업 사고가 보이는가 | 아래 30분 설계 풀이 |
| 역량/인적성 | 검사별 요구 역량과 일하는 성향 | 공식 안내 확인·연습·환경 점검 |
| 컬처핏/임원 | 어떤 기준으로 일하고 책임지는가 | 행동 사례·가치관·업종 전환 이유 |
| 레퍼런스 | 경력 설명과 동료가 본 행동이 일치하는가 | 날짜·역할·협업 범위 사실 확인 |
| 처우/오퍼 | 기대 역할·보상·조건을 합의할 수 있는가 | 실제 희망 범위와 입사 일정 |

발표·디자인 사고·협업을 별도 세션으로 확인하는 공식 사례도 있습니다. [Duolingo 면접 안내](https://blog.duolingo.com/product-design-interviews/)는 이 구분을 이해하기 위한 예시이며 국내 모든 회사의 전형으로 일반화하지 않습니다.

## 2. 리크루터 통화: 짧게 말하는 답변

### R01. 간단히 경력 소개 부탁드립니다.

> 2020년 웹디자인과 퍼블리싱으로 시작했고, 2022년 말부터 B2B 플랫폼과 ERP, 모바일 업무 서비스의 UX/UI로 경험을 넓혔습니다. 업무의 정보 구조와 상태를 화면으로 구체화하고 구현 기준까지 연결한 것이 강점입니다. 현재는 다른 산업의 제품으로 이 경험을 확장할 기회를 찾고 있습니다.

### R02. 어떤 포지션을 찾고 있나요?

> UX/UI 또는 프로덕트 디자이너로, 사용자의 입력·조회·탐색 흐름과 복잡한 정보를 정리하는 역할에 관심이 있습니다. 산업은 넓게 보고 있고 기존 토목·건축 분야 밖에서 경험을 확장하고 싶습니다. 직함만으로 결정하기보다 팀이 기대하는 업무와 제 강점이 맞는지 확인하고 있습니다.

### R03. 너무 폭넓게 지원하는 것 아닌가요?

> 업종은 넓게 보지만 역할의 기준은 있습니다. 사용자가 처리해야 할 과업이 명확하고, 제가 정보 구조·UI·구현 협업으로 기여할 수 있는지 보겠습니다. 제품의 핵심 문제가 무엇인지와 디자이너의 책임 범위를 확인해 지원 이유를 구체화하고 있습니다.

### R04. 출근·입사 가능일은요?

> 현재 상황과 인수인계 일정을 고려한 실제 가능일은 [본인 사실 입력: 날짜 또는 기간]입니다. 전형 일정과 회사의 필요 시점을 확인한 뒤 가능한 조정 범위를 말씀드리겠습니다.

재직/퇴사 여부를 추측하지 않습니다. 현재 자료는 이력상 재직 중으로 표시돼 있으므로 변경됐다면 지원 서류부터 맞춥니다.

### R05. 원하는 레벨은요?

> 전체 경력은 6년 이상이지만 웹디자인·퍼블리싱과 B2B 제품 설계 경험의 비중을 구분해서 보고 있습니다. 바로 기여할 수 있는 역할과 기대 책임을 기준으로 협의하고 싶습니다. 사람 관리가 핵심인 리드 역할보다는 실제 제품 문제를 맡는 역할과의 적합도를 먼저 보겠습니다.

## 3. 컬처핏·행동 면접 20문답

아래에서 **[본인 사실 입력]**은 암기 전에 실제 경험으로 완성해야 합니다. 실제 확인되지 않은 갈등·실패·감정·동료 평가를 허구의 1인칭 이야기로 제공하지 않았습니다. 답변의 구조와 포트폴리오 근거는 바로 사용할 수 있습니다.

### C01. 왜 산업을 바꾸려고 하나요?

> 현업의 복잡한 정보를 이해하고 기록·조회·확인 화면으로 만드는 기반을 쌓았습니다. 이제 이 역량을 새로운 사용자와 제품 맥락에 적용하고 싶습니다. 도메인이 바뀌어도 업무를 배우고 과업과 상태로 구조화하는 방식은 이어갈 수 있다고 생각합니다. 지원 제품에서 제가 무엇을 배워야 하고 무엇으로 기여할 수 있는지 함께 보고 있습니다.

### C02. 낯선 산업에서 적응할 수 있나요?

> 익숙한 용어부터 화면에 대입하기보다 사용자·업무·데이터·정책을 먼저 나누겠습니다. 실제 한 건이 시작해서 끝나는 과정을 현업과 함께 따라가며 모르는 용어와 예외를 정리하고, 제가 이해한 흐름을 다시 확인받겠습니다. 도메인을 모르는 상태에서 결정권을 먼저 주장하기보다 질문과 시각화로 빠르게 합의를 만들겠습니다.

### C03. 좋은 동료란 어떤 사람인가요?

> 같은 의견을 내는 사람보다 판단에 필요한 정보와 제약을 일찍 공유하는 사람이라고 생각합니다. 저도 시안만 보여주기보다 무엇을 해결하려는지, 어디가 결정됐고 어디가 아직 가정인지 설명하는 동료가 되고 싶습니다. 문제가 생겼을 때 개인의 잘못을 먼저 찾기보다 해결할 작업과 책임 범위를 명확히 하는 태도를 중요하게 봅니다.

이 가치관이 본인과 다르면 실제 생각으로 바꾸세요.

### C04. 의견 충돌을 해결한 실제 사례를 말해주세요.

**이 항목은 사실 입력이 필요합니다. 메뉴 시안 비교를 갈등 사건으로 바꾸지 마세요.**

> [실제 프로젝트]에서 [상대 직군]은 [실제 주장/제약]을 중요하게 봤고, 저는 [근거] 때문에 [다른 안]을 제안했습니다. 먼저 [함께 확인한 목표]를 맞췄고 [화면/프로토타입/작업량 비교]로 차이를 구체화했습니다. 최종적으로 [실제 합의]했고 결과는 [확인한 범위]였습니다. 이 경험 이후 [바뀐 행동]을 하고 있습니다.

꼬리 대비: 상대의 주장을 공정하게 설명할 수 있는가? 내 안이 선택되지 않았다면 어떻게 했는가? 실제로 감수한 손해는 무엇인가?

### C05. 실패한 경험은 무엇인가요?

> ERP에서는 웹 UI를 설계하고 퍼블리싱했지만, 최종 제공 형식이 PDF로 바뀌어 웹 설계안이 사용되지 않았습니다. 제가 설계한 화면이 최종 사용으로 이어지지 않았다는 결과를 분명히 보고 있습니다. 이 경험을 통해 화면보다 먼저 정보 소비 방식과 산출물 형식을 합의해야 한다는 점을 배웠습니다. 다음에는 누가 직접 조회하고 누가 보고서를 받는지 초기에 확인하겠습니다.

책임 질문에는 당시 자신의 확인 부족과 개선 행동을 말합니다. 변경의 원인을 전부 본인 탓이나 다른 팀 탓으로 확정하지 않습니다.

### C06. 비판적인 피드백을 받고 바꾼 경험은요?

**[본인 사실 입력]** 실제 피드백의 발신자·내용·수정·결과가 필요합니다.

> [실제 피드백]을 처음에는 [실제 반응]으로 받아들였습니다. 다만 취향의 차이인지 과업에 관한 문제인지 확인하기 위해 [한 행동]을 했습니다. 이후 [실제 수정]했고 [확인 결과]를 얻었습니다. 지금은 피드백을 받으면 의도와 해결할 문제를 먼저 되묻습니다.

반려동물 홈의 우선순위 수정은 설명 가능한 설계 변화입니다. 하지만 누군가의 사용자 테스트 결과 때문에 바꿨다고 말할 근거는 없습니다.

### C07. 주도적으로 한 일을 말해주세요.

> 제가 구체적으로 설명할 수 있는 주도적 판단은 플랫폼 메뉴의 UI 대안 비교입니다. 기획 방향은 주어진 상태였지만, 지도 연속성과 메뉴 구분이라는 기준으로 세 배경안을 비교하고 반투명 검정안을 선택해 구현했습니다. 방향을 만든 사람과 표현을 결정한 제 역할을 구분해서 설명드릴 수 있습니다.

더 강한 범위·일정 조율의 사례가 있다면 실제로 한 행동을 추가합니다.

### C08. 급한 요청으로 일이 늘어나면요?

> 요청의 마감 이유와 사용자가 겪는 영향을 확인하고, 현재 작업과 의존성을 함께 보겠습니다. 반드시 필요한 부분과 다음 단계로 나눌 수 있는 부분을 제안하고 일정에 미치는 영향을 공유하겠습니다. TBM에서는 담당자 요청으로 파일 열람 UI를 추가 제작한 경험이 있습니다. 당시 일정 조정의 구체적인 방법은 제가 실제 기억하는 범위로 말씀드리겠습니다.

### C09. 본인의 단점은 무엇인가요?

아래는 **실제로 일치할 때만 사용할 초안**입니다.

> 요구사항을 화면으로 구체화하는 데 집중한 반면, 성공 기준과 결과 확인 방법을 초기에 충분히 남기지 못한 점이 있습니다. 그래서 배포 사실과 사용성 개선을 구분해 설명하고 있습니다. 다음 프로젝트에서는 핵심 과업과 확인할 지표, 사용자 접점을 시작 단계의 합의 항목으로 넣겠습니다.

관찰되지 않은 “요즘 이미 매주 테스트합니다” 같은 완료형 변화는 넣지 않습니다.

### C10. 완성도와 속도 중 무엇이 더 중요한가요?

> 시점과 실패 비용에 따라 기준이 달라진다고 생각합니다. 방향을 확인하는 초기 단계에서는 핵심 가정을 빠르게 보여주고, 실제 사용 전에는 입력 손실이나 잘못된 완료처럼 업무에 영향을 주는 상태를 꼼꼼히 확인해야 합니다. 무엇을 빠르게 하고 무엇을 놓치면 안 되는지 팀과 합의하겠습니다.

### C11. 상사가 근거 없이 시안을 바꾸라고 하면요?

> 우선 바꾸려는 이유와 중요하게 보는 대상을 물어보겠습니다. 목적이 분명해지면 대안을 비교하고 사용자 과업에 미치는 영향을 설명하겠습니다. 최종 결정이 다른 안이라면 합의 내용을 따르면서 확인할 위험과 추후 검증 항목을 남기겠습니다. 매번 제 안이 선택돼야 협업이 잘된다고 생각하지는 않습니다.

### C12. 내 판단이 틀렸다는 걸 알게 되면요?

> 어떤 가정이 틀렸는지 먼저 구분하고, 현재 사용자에게 미치는 영향과 수정 범위를 공유하겠습니다. 이전 결정을 방어하기보다 새 근거에 맞춰 바꾸는 것이 중요하다고 생각합니다. 사소한 표현은 바로 수정할 수 있지만 범위나 일정이 바뀌는 결정은 관계자와 다시 합의하겠습니다.

### C13. 불합리한 일정이면 어떻게 하나요?

> 할 수 없다는 결론만 말하기보다 남은 작업·의존성·핵심 위험을 보여주고, 범위 축소나 단계적 공개의 대안을 제안하겠습니다. 일정이 고정이라면 핵심 과업과 필수 상태를 먼저 지키고 어떤 항목을 뒤로 미룰지 합의하겠습니다. 실제 있었던 일정 사례는 [본인 사실 입력]으로 준비하겠습니다.

### C14. 혼자 일하는 게 좋은가요, 협업이 좋은가요?

> 혼자 집중해 구체화하는 시간과 다른 직군과 방향을 맞추는 시간이 모두 필요합니다. 저는 UI·퍼블리싱으로 구체적인 결과를 만드는 데 강점이 있고, 기획·개발·엔지니어와 요구사항을 조율해 왔습니다. 협업에서는 언제 무엇을 확인받아야 재작업을 줄일 수 있는지 의식하겠습니다.

### C15. 회사가 기대한 성과를 못 내면요?

> 처음 합의한 목표와 기대 역할부터 확인하고, 결과가 부족한 이유를 문제 선택·실행·검증으로 나눠 보겠습니다. 필요한 도움과 바꿀 행동을 정해 작은 범위부터 개선하고, 진행 상황을 공유하겠습니다. 개인의 노력을 강조하는 것보다 실제 결과와 다음 행동을 투명하게 말하겠습니다.

### C16. 팀에서 인정받았던 강점은요?

> 현재 자료에서 확인되는 피드백은 플랫폼 메뉴가 나뉘어 구분이 명확하고 사용하기 좋다는 내부 동료 의견입니다. 이 의견을 제 전반적인 동료 평판으로 확대하지는 않겠습니다. 더 넓은 평가를 말씀드리려면 [실제 동료 피드백]과 그 배경 행동을 예로 들겠습니다.

### C17. 디자이너의 책임은 어디까지인가요?

> 맡은 화면의 미적 완성도뿐 아니라 사용자가 과업을 이해하고 완료할 수 있는지, 구현 과정에서 의도가 유지되는지까지 관심을 가져야 한다고 생각합니다. 권한과 전문성이 다른 부분은 협업하고, 제가 확인하지 못한 것을 완료로 보고하지 않겠습니다. 제품 성과는 여러 직군의 기여라는 점도 구분하겠습니다.

### C18. 왜 당신을 뽑아야 하나요?

> 복잡한 업무의 정보와 상태를 UI와 구현 기준으로 구체화할 사람이 필요하다면 기여할 수 있습니다. 플랫폼 메뉴, 모바일 기록·서명, 비용·인원 조회 화면을 다뤘고 HTML·CSS·SCSS 퍼블리싱 기반으로 개발자와 협의할 수 있습니다. 성장 실험 경험의 부족은 인정하되, 제가 바로 맡을 수 있는 문제와 배워야 할 범위를 분명히 가져가겠습니다.

### C19. 3년 뒤 어떤 디자이너가 되고 싶나요?

> 업무와 화면을 구체화하는 강점에 더해, 어떤 문제를 먼저 풀어야 하는지와 개선 결과까지 설명할 수 있는 디자이너가 되고 싶습니다. 익숙한 화면을 만드는 사람보다 새로운 도메인을 배우고 팀과 근거를 공유하며 제품을 꾸준히 개선하는 사람이 목표입니다.

### C20. 합격하면 오래 다닐 건가요?

> 새로운 업종을 경험하는 것 자체보다 한 제품에서 사용자와 업무를 이해하고 개선 결과를 쌓는 역할을 찾고 있습니다. 그래서 지원할 때 기대 업무와 의사결정 방식, 사용자와 결과를 확인할 수 있는 환경을 중요하게 봅니다. 장기적으로 기여할 수 있는 역할인지 충분히 확인하고 결정하고 싶습니다.

본인이 실제로 중요하게 보는 근무 조건과 가치도 숨기지 않고 일관되게 설명합니다.

## 4. 실제 행동 사례 여섯 장 만들기

면접관은 같은 사건을 다른 방향으로 질문합니다. 사례를 많이 꾸미기보다 아래 여섯 장을 사실로 완성하세요.

| 카드 | 바로 쓸 수 있는 근거 | 본인이 추가해야 할 정보 |
|---|---|---|
| 선택·판단 | 플랫폼 배경 3안 비교 | 당시 비교·협의 방식, 자신이 맡은 작업 |
| 협업·갈등 | 기획/개발과 조율 경험 | 실제 의견 차이 사건 1개, 상대 근거, 합의 |
| 결과가 안 난 경험 | ERP 웹 최종 미사용 | 변경 시점·내 대응·이후 실제 바뀐 행동 |
| 추가 요구·범위 | TBM 파일 열람 추가 | 실제 일정·개발 협의·우선순위 조정 여부 |
| 피드백·수정 | 본인 실제 사례 필요 | 누가 무엇을 말했고 무엇을 바꿨는지 |
| 학습·한계 발견 | 칸반 프로토타입, React 학습 | 직접 이해한 코드·막힌 점·해결 과정 |

각 카드의 형식: **상황 1문장 → 목표와 내 역할 1문장 → 내가 한 행동 2문장 → 확인한 결과 1문장 → 다음 행동 1문장**. 각 문장을 왜 그렇게 했는지 묻는 꼬리 질문 두 개를 만듭니다.

## 5. 사전 과제: 제출물의 구성

### 시작 문장

> 제한된 시간 안에서 [사용자]의 [핵심 과업]을 우선 해결하는 방향으로 범위를 정했습니다. 확인된 정보와 가정을 나누고, 가장 영향이 큰 가정부터 검증 가능한 형태로 제안하겠습니다.

### 작업 순서

1. 공고·과제에서 반드시 지킬 범위, 시간, 산출물, 도구·AI 사용 조건을 읽습니다.
2. 사용자·업무·문제·사업 목적·제약·모르는 것을 한 페이지로 적습니다.
3. 핵심 흐름 하나를 선택하고 현재 방식의 어려움과 가설을 정리합니다.
4. 최소 두 대안을 비교한 뒤 한 안을 선택합니다. 장단점을 실제 사용자 행동으로 설명합니다.
5. 정상 흐름과 중요한 실패 상태를 만듭니다. UI를 과도하게 늘리지 않습니다.
6. 검증할 과업과 성공·보호 지표, 다음 우선순위를 적습니다.
7. 실제 근거와 추측을 다시 구분하고 최종 발표를 연습합니다.

### 예시 시간 배분: 총 6시간 과제

| 시간 | 작업 |
|---|---|
| 0:00–0:40 | 문제·대상·제약·가정 |
| 0:40–1:20 | 흐름·핵심 우선순위·대안 |
| 1:20–3:40 | 주요 화면과 중요한 상태 |
| 3:40–4:30 | 프로토타입·텍스트·정합성 |
| 4:30–5:20 | 근거·검증·한계 정리 |
| 5:20–6:00 | QA·발표 리허설·제출 확인 |

이 일정은 연습용 제안입니다. 회사가 정한 시간과 요구 산출물이 우선입니다.

### 제출 설명의 일곱 항목

- 누구의 어떤 과업인가.
- 확인한 사실과 가정은 무엇인가.
- 무엇을 가장 먼저 해결하기로 했는가.
- 대안과 선택 기준은 무엇인가.
- 정상·예외 흐름은 어떻게 이어지는가.
- 결과를 어떻게 검증할 것인가.
- 시간 때문에 제외한 항목과 다음 확인은 무엇인가.

과제용 사용자 인터뷰·지표를 꾸며 넣지 않습니다. 실제로 테스트하지 않았다면 “검증 계획”입니다. AI 사용은 회사 조건을 확인하고, 허용될 때도 도움 받은 부분과 본인 판단을 분리합니다.

## 6. 30분 라이브 디자인: 회의실 예약 예제

**연습용 가상 문제**: 직원이 모바일에서 회의실을 찾고 예약할 수 있게 설계해 주세요. 기존 인트라넷의 출시 성과를 설명하는 문제가 아닙니다.

### 0–3분: 질문하기

> 먼저 몇 가지 확인하겠습니다. 주 사용자는 반복 예약하는 직원인가요, 가끔 예약하는 직원인가요? 한 사무실만 대상으로 하나요? 가장 큰 문제는 빈 방 찾기, 예약 입력, 현장 중복 중 무엇인가요? 이번 과제에서는 예약 변경·취소까지 포함하나요?

대답을 못 받으면 “한 사무실 직원이 오늘 사용할 방을 즉시 예약하는 과업으로 가정하겠습니다”라고 범위를 선언합니다.

### 3–7분: 문제와 성공 기준

> 오늘 회의를 잡아야 하는 직원이 수용 인원과 시간에 맞는 방을 찾아 충돌 없이 예약하는 것을 핵심 과업으로 잡겠습니다. 우선 예약 완료율과 소요 시간, 충돌·중복 시도, 잘못 예약한 뒤 취소하는 비율을 보겠습니다. 실제 기존 수치는 제공되지 않아 목표 변화율은 정하지 않겠습니다.

### 7–12분: 흐름과 대안

> 먼저 시간과 인원을 고른 뒤 가능한 방을 보여주는 안과, 방 목록에서 각각 시간을 확인하는 안을 비교하겠습니다. 지금 가정한 사용자는 오늘 특정 시간에 방이 필요하므로 시간 조건을 먼저 넣는 안을 선택하겠습니다. 반면 특정 장비나 방을 고정해서 쓰는 사용자는 방 중심 탐색도 필요할 수 있습니다.

핵심 흐름: 조건 선택 → 가능한 방 목록 → 방 상세/시간 확인 → 예약 확인 → 서버 성공 결과.

### 12–22분: 주요 화면과 상태

- 조건: 날짜·시작/종료 시간·인원. 필요한 경우 장비 필터.
- 목록: 방명·수용 인원·가능 시간·위치. 선택 이유가 되는 정보부터.
- 확인: 방·날짜·시간·참석 인원·목적을 검토.
- 결과: 성공이 확인된 예약 내용과 변경/취소 진입.
- 예외: 검색 결과 없음, 다른 사용자가 먼저 예약함, 네트워크 실패, 성공 여부를 확인할 수 없음.

> 예약 버튼을 눌렀다는 이유만으로 완료를 표시하지 않고, 서버에서 확정된 결과를 기준으로 보여주겠습니다. 충돌하면 입력 조건을 유지한 채 다른 방이나 시간을 찾도록 하겠습니다.

### 22–27분: 검증과 트레이드오프

> 시간 조건부터 고르는 흐름이 실제 예약 목적과 맞는지 과업 테스트로 확인하겠습니다. 가장 먼저 성공 여부와 충돌 후 복구를 보겠습니다. 방의 모든 정보를 첫 화면에 넣지 않은 대신, 장비나 접근성 조건이 중요한 사용자에게 필요한 정보가 빠지지 않았는지도 확인하겠습니다.

### 27–30분: 요약

> 오늘은 특정 시간에 방을 찾는 과업에 집중했습니다. 시간 조건을 먼저 정하고 가능한 방을 선택하게 했고, 서버에서 예약이 확정되기 전과 완료된 상태를 구분했습니다. 다음에는 반복 예약·변경·취소와 실제 사무실의 정책을 확인하겠습니다.

## 7. 화면 비평 면접: 5분 답변 순서

가상 상황: 대시보드를 보여주며 “어떤 점을 개선하겠습니까?”라고 묻습니다.

> 먼저 이 화면의 사용자와 핵심 결정을 확인하고 싶습니다. 현재 화면에서는 [실제로 보이는 사실]이 보입니다. 이 때문에 [가설상 과업 어려움]이 있을 수 있지만 실제 사용 데이터는 확인하지 못했습니다. 우선 [가장 중요한 문제 하나]를 개선하고, [과업]에서 [성공 기준]으로 확인하겠습니다.

우선순위: 목적·정보 위계 → 상태·주요 행동 → 가독성·정렬 → 예외·반응형. 마음에 안 드는 색부터 비판하지 않습니다. 경쟁 제품을 본인 취향으로 폄하하지 않고, 사업·정책상 이유를 모르는 상태임을 구분합니다.

## 8. 역량검사·AI 영상면접·인적성

### 검사 종류를 먼저 구분

인지/수리/언어/추리 검사, 일하는 성향을 묻는 검사, 전략 게임, 영상 응답은 준비 방식이 다릅니다. 특정 회사의 초대에 포함된 제품명·버전·구성·응시 환경을 확인하세요. 모든 검사에 카메라나 동일한 게임이 있다고 가정하지 않습니다.

[JOBDA 공식 역량검사 안내](https://www.jobda.im/acca/test)에서 현재 안내를 확인하고, 초대된 검사와 일치하는 공식 연습을 선택합니다. [구 역량검사 튜토리얼](https://www.jobda.im/acc/tutorial)은 성향·전략게임·영상면접 연습을 안내하지만 구 버전 페이지이므로 현재 검사와 동일한 구성이라고 생각하지 않습니다.

### 성향 문항

실제 일할 때 반복되는 행동을 기준으로 응답합니다. 전부 리더형·도전형·완벽주의형으로 맞추려 하지 않습니다. “협업을 선호한다”와 “의견 차이를 말한다”는 반드시 모순이 아닙니다. 문항을 과하게 해석하기보다 조건과 빈도를 읽고 일관된 실제 행동으로 응답하세요. 합격하는 성격 조합이나 비공개 채점 공식을 알고 있다고 주장할 근거는 없습니다.

### 전략 게임·인지 검사

규칙을 이해하는 연습과 실제 평가를 구분합니다. 허용된 공식 연습에서 목표·입력 방식·제한 시간·실수 복구를 익히세요. 실전에서는 한 번의 실수에 매달리지 않고 현재 문항의 규칙으로 돌아옵니다. 외부 도움·메모·계산기·재응시가 허용되는지는 회사 안내를 확인합니다.

### 영상 응답의 기본 형식: 60–90초

- 0–10초: 질문에 대한 결론.
- 10–25초: 실제 상황과 내 역할.
- 25–55초: 내가 한 행동과 이유.
- 55–75초: 확인한 결과와 한계.
- 75–90초: 배운 점 또는 지원 역할과 연결.

정확한 발화 시간은 안내에 맞춥니다. 억지 미소·특정 시선 각도가 합격 점수를 만든다는 식의 준비는 하지 않습니다. 목소리가 들리고 표정이 자연스럽게 보이는 환경, 질문에 답하는 내용과 시간 준수를 우선합니다.

### 영상면접 연습 질문 여덟 개

1. 1분 자기소개 → 핵심 카드 3번.
2. 원하는 결과를 만든 경험 → 플랫폼 시안 비교·배포. 측정되지 않은 효과 수치 제외.
3. 원하는 결과가 안 난 경험 → ERP 미사용과 제공 형식 합의.
4. 갈등 해결 → C04에 실제 사례 입력 후 사용.
5. 새로운 것을 배운 경험 → 칸반 AI 보조 구현 또는 React. 실제 막힌 점 포함.
6. 업무가 몰리면 → 심각도·기한·의존성·범위 협의. 실제 사건이면 사실로 보완.
7. 리더/구성원 역할 → 실제 역할 기준. 공식 리딩 경험을 가정하지 않음.
8. 지원 이유 → 회사별 네 문장. 공통 성장 욕구만 반복하지 않음.

### 창작 연습 문제: 검사 기출이 아님

**수리 1**: 작성 시작 160건 중 서버 저장 성공 120건. 완료율은? → 120/160 = 75%. 다음 주 80%이면 **5%p 상승**, 상대 증가율은 약 6.7%. “5% 증가”와 구분합니다.

**수리 2**: 완료 시간이 12분에서 9분으로 줄었다면? → 3분 감소, 기존 대비 25% 감소. 이것은 가상 연습 수치이며 포트폴리오 실적으로 사용하지 않습니다.

**추리**: “모든 승인된 문서는 저장됐다. 저장된 일부 문서는 검토 전이다.” 승인된 문서는 모두 검토를 마쳤다고 말할 수 있나? → 주어진 두 문장만으로는 판단할 수 없습니다. 업무 상식이 아니라 제시된 조건을 따라야 합니다.

**주의력**: A-104, A-140, A-104, A-014 중 같은 코드는? → 1번과 3번. 빠르게 추측하기보다 기준 단위를 유지합니다.

**자료 해석**: 완료율이 높아졌지만 신규 사용자가 크게 줄었다면 개선 성공인가? → 사용자 구성 변화 가능성이 있어 단정할 수 없습니다. 동일 집단과 과업 조건을 비교해야 합니다.

### 응시 전 점검

초대 링크·기한·지원 브라우저·장비·오디오·네트워크·신분 확인 조건·허용 도구를 확인합니다. 공식 테스트를 통해 환경을 먼저 점검하고, 결과를 제출하기 전 제출 완료 여부를 확인합니다. 실제 평가 중에는 외부 답변 지원을 받는 대신 안내된 응시 규칙을 따릅니다.

## 9. 임원·최종 면접

### 왜 웹디자이너에서 프로덕트 디자이너로 오려고 하나요?

> 초기에는 기업 웹 UI와 반응형·퍼블리싱을 다뤘고, 이후 업무 플랫폼과 모바일 기록·대시보드로 경험을 넓혔습니다. 정보의 표현뿐 아니라 사용자가 처리하는 과업과 상태를 설계하는 일에 경험이 쌓였습니다. 다음에는 이 기반을 제품의 문제 선택과 출시 후 개선까지 연결하고 싶습니다.

### 새 산업에서는 처음부터 다시 배워야 하지 않나요?

> 도메인 지식은 새로 배워야 합니다. 다만 사용자 역할과 과업, 데이터가 생성되고 소비되는 흐름을 파악해 UI로 구조화하는 방식은 가져갈 수 있습니다. 모르는 산업을 이미 안다고 하기보다 실제 업무 한 건을 따라가며 빨리 배우고, 이해한 구조를 팀과 확인하는 방식으로 적응하겠습니다.

### 회사에 어떤 가치를 만들 수 있나요?

> 입력·조회·상태가 복잡한 제품에서 사용자가 이해하고 처리할 수 있는 화면으로 구체화하는 데 기여할 수 있습니다. 구현 협업 경험도 있어 설계와 개발 사이의 기준을 맞추는 데 도움이 됩니다. 입사 후에는 팀의 핵심 문제 하나와 성공 기준을 합의해 실제 결과로 연결하고 싶습니다.

## 10. 레퍼런스·처우·최종 선택

### 레퍼런스 준비

추천인에게 연락하기 전 본인의 실제 협업 범위와 함께 한 프로젝트를 정리합니다. 추천인의 사전 동의를 받고 회사가 요청한 공식 절차로 진행합니다. 이 자료는 연락을 대신 보내지 않습니다. 상대에게 특정 평가나 허위 답변을 요청하지 않습니다.

정합성 목록: 회사·기간·직함·프로젝트·내 역할·협업 상대·최종 사용 상태·현재 재직 여부. “총경력 6년”과 “6년간 제품 성장 지표를 주도”는 같은 말이 아닙니다.

### 희망 연봉

> 제가 생각하는 범위는 [실제 희망 범위]입니다. 다만 팀이 기대하는 역할과 레벨, 기본급·변동 보상·기타 조건을 함께 확인하고 협의하고 싶습니다.

실제 최소 수용 조건과 희망을 구분해 미리 적습니다. 현재 보상이나 다른 오퍼 금액을 꾸며 협상하지 않습니다. 특정 금액을 이 자료만으로 정하지 않습니다.

### 오퍼를 받았을 때 확인할 내용

실제 업무·레벨·보고 관계·평가 기준·수습 조건·보상 구성·근무 방식·입사일을 확인합니다. 궁금한 조건은 문서로 확인하고, 토목·건축 밖의 역할인지 공고 제목뿐 아니라 주요 고객·제품·배정 업무로 확인합니다. 구체적인 계약 문제는 개별 문서를 보고 따로 검토해야 합니다.

# 실전 훈련·지원 전략·회사 맞춤

## 1. 폭넓게 지원하되 설명의 중심은 정하기

아래는 현재 포트폴리오의 근거로 판단한 지원 전략입니다. 특정 회사의 채용 가능성이나 합격률을 예측한 것은 아닙니다. 실제 공고의 필수 요건과 업무를 확인해 분류합니다.

| 구분 | 공고에서 찾을 역할 | 지금 연결할 근거 | 주의할 기대 차이 |
|---|---|---|---|
| 우선 지원 | B2B SaaS, 운영/어드민, 데이터 조회, 입력/승인 업무 | 플랫폼·TBM·ERP의 정보 구조와 상태, 퍼블리싱 | ERP 미사용·정량 검증의 깊이 |
| 우선 지원 | 웹 UX/UI, 서비스 웹, 반응형 리뉴얼 | 스카이오토넷·테스콤·구현 협업 | 브랜드 웹만 계속 맡는지 실제 업무 확인 |
| 확장 지원 | HR·협업·교육·커머스 운영·금융 운영 | 기록·신청·조회·탐색의 공통 구조 | 업종 지식·정책은 새로 배워야 함 |
| 확장 지원 | B2C 모바일 프로덕트 | TBM 모바일과 개인 기록 앱 | 소비자 리서치·리텐션·출시 성과 근거 부족 |
| 선별 지원 | 디자인 시스템 전담 시니어 | 컬러 변수·상태 가이드·일부 재사용 | 조직 운영·라이브러리 체계화 경험 차이 |
| 선별 지원 | 성장 실험 중심 시니어·리드·매니저 | 구현과 업무 구조화 경험 | 반복 실험·전략·사람 관리 필수 경험 확인 |

토목·건축 제외는 공고의 회사 업종뿐 아니라 담당 제품과 고객으로 확인합니다. 예를 들어 일반 소프트웨어 회사여도 건설 고객 전담 제품이면 사용자 선호와 다를 수 있습니다. 부동산·공간 서비스처럼 경계가 애매한 공고는 본인이 원하는 업무인지 따로 판단합니다.

## 2. 공고 하나를 20분 안에 읽는 방법

### 0–5분: 역할 분해

실제 산출물, 핵심 사용자, 문제 정의 참여 범위, 출시 후 책임, 필수 경험, 근무 조건을 표시합니다. “프로덕트 디자이너”라는 직함만 보고 동일한 일을 기대하지 않습니다.

### 5–10분: 제품의 핵심 과업 하나 따라가기

가입·검색·신청·구매·조회 등 실제 접근 가능한 과업을 수행합니다. 화면에서 관찰한 사실과 불편할 것이라는 가정을 분리합니다. 계정이나 결제가 필요해 접근하지 못했다면 공식 제품 설명·도움말을 확인하고 그 범위를 적습니다.

### 10–15분: 나의 사례 연결

필수 요구 세 가지 옆에 경험을 연결합니다. 직접 근거가 없는 항목은 빈칸으로 둡니다. “데이터 기반 의사결정” 요구에 가상 숫자가 들어간 대시보드 이미지를 증빙으로 넣지 않습니다.

### 15–20분: 지원 동기 네 문장·역질문 두 개

사용자/과업 → 관찰 → 내 실제 기여 → 확인할 가설을 작성합니다. 면접관에게 물어볼 것은 제품과 역할에 관한 진짜 미확인 정보입니다.

## 3. 업종별 지원 동기 초안

아래는 회사 고유 지원 동기를 완성하기 위한 초안입니다. **[제품명·실제로 관찰한 내용]**을 넣어야 사용 가능합니다. 각 산업의 일반 특성을 해당 회사의 사실처럼 말하지 않습니다.

### B2B SaaS·운영 도구

> 귀사의 [제품]에서 [담당자]가 [반복 업무]를 처리하는 흐름에 관심이 있습니다. [실제 사용/공식 설명]에서 [관찰 사실]을 확인했습니다. 저는 플랫폼의 메뉴와 ERP 조회 조건·요약·상세를 설계한 경험이 있어, 복잡한 정보를 사용 목적에 맞게 구체화하는 데 기여할 수 있습니다. 입사 후에는 실제 운영자가 자주 막히는 과업과 확인 기준을 먼저 이해하고 싶습니다.

### HR·협업 서비스

> 귀사의 [제품]이 [사용자]의 [신청·협업 과업]을 연결하는 방식에 관심이 있습니다. [관찰 사실]을 확인했고, 사용자별 상태와 다음 행동을 이해하는 경험이 중요하다고 생각했습니다. 저는 모바일 기록·확인·서명과 팀 프로젝트의 신청 화면을 설계한 경험이 있습니다. 실제 정책과 예외를 배우며 신청 시작부터 결과 확인까지 이어지는 흐름을 개선하고 싶습니다.

### 커머스·플랫폼

> 귀사의 [제품]에서 [사용자]가 [탐색/비교/운영 과업]을 처리하는 흐름에 관심이 있습니다. [관찰 사실]을 바탕으로 정보의 우선순위와 다음 탐색이 중요하다고 봤습니다. 저는 제품·솔루션 탐색 구조와 반응형 UI, 복잡한 메뉴를 설계한 경험을 연결할 수 있습니다. 구매 전환 실험을 주도한 경력은 없으므로 그 부분은 팀의 데이터와 사용자 맥락을 배우며 보완하겠습니다.

### 금융·핀테크

> 귀사의 [제품]에서 [사용자]가 [조회/검토/거래 과업]을 이해하고 실행하는 흐름에 관심이 있습니다. [관찰 사실]을 확인했고 숫자의 맥락과 상태를 명확히 전달하는 일이 중요하다고 생각했습니다. 비용·인원 화면에서 조회 조건과 요약·상세, 초과 상태를 구분했던 경험을 연결할 수 있습니다. 금융 정책과 규정에 대한 실무 지식은 새로 학습하면서 해당 영역의 담당자와 확인하겠습니다.

### 교육·콘텐츠 서비스

> 귀사의 [제품]에서 [사용자]가 [탐색/학습/기록 과업]을 이어가는 방식에 관심이 있습니다. [관찰 사실]과 제 웹 탐색·모바일 기록 UI 경험을 연결할 수 있다고 생각했습니다. 개인 앱에서 빠른 기록과 진행 상태를 구성했지만 반복 사용 효과를 검증한 단계는 아닙니다. 실제 사용자가 어느 구간에서 중단하는지 확인하며 설계를 발전시키고 싶습니다.

### B2C 모바일·생활 서비스

> 귀사의 [제품]이 [사용자]의 [구체 과업]을 돕는 방식에 관심이 있습니다. [관찰 사실]을 보며 첫 진입에서 무엇을 해야 할지 이해하는 경험을 중요하게 봤습니다. 모바일 일지의 작성 맥락과 확인 상태, 개인 기록 앱의 우선순위를 설계한 경험을 가져갈 수 있습니다. 소비자의 이용 동기와 반복 사용은 제 기존 업무 앱 경험과 다를 수 있어 직접 확인하며 배우고 싶습니다.

|---|---|---|
| 1일 | 핵심 카드 1–6, 경력 기간·역할 점검 | 30초/1분 소개를 보지 않고 말함 |
| 2일 | 플랫폼 4–10쪽, 대안 비교 연습 | 기획자와 내 역할을 정확히 구분 |
| 3일 | TBM 11–15쪽, 상태와 추가 요청 | 서명 저장/일지 제출 차이 설명 |
| 4일 | 두 사례 10분 PT 녹화 | 제한 시간 안에 결과·한계까지 마침 |
| 5일 | ERP·공통 UI, 취약 질문 | 미사용·일부 재사용을 숨기지 않음 |
| 6일 | Q01–Q30 무작위 10문항 | 질문당 핵심 답변 60초 이내 |
| 7일 | 실제 행동 사례 여섯 장 | 갈등·피드백의 실제 사건 채움 |
| 8일 | Q31–Q45, 과업·지표·우선순위 | 지표의 분모·분자·예외 설명 |
| 9일 | Q46–Q60, Figma/코드 확인 | 실제 파일·상태·구현 범위를 시연 |
| 10일 | 라이브 예약 설계 30분 | 확인 질문→선택→예외→검증을 마침 |
| 11일 | 컬처핏 20문항과 90초 영상 | 사실·주장·제안이 구분됨 |
| 12일 | 검사 공식 안내·허용 연습 | 규칙과 환경이 익숙함 |
| 13일 | 목표 공고 3개를 분석 | 각 회사 지원 동기·사례·역질문 완성 |
| 14일 | 60분 모의면접과 최종 점검 | 아래 점검표의 사실 오류 0개 |

하루 공통 루틴: 자기소개 1회 → 랜덤 질문 5개 → 화면 근거 1개 → 어색한 답변 1개만 수정. 한 답변을 오래 외우느라 전체 경험의 정합성을 놓치지 않습니다.

## 5. 면접이 내일일 때: 3시간 압축

- 0–25분: 자기소개·업종 전환·연차·지원 동기 네 문장.
- 25–65분: 플랫폼과 TBM 대본을 화면과 연결해서 2회.
- 65–90분: 성과 수치 없음·ERP 미사용·React·AI·공통 UI 범위.
- 90–120분: 실제 갈등·실패·피드백·학습 사례. 확인되지 않은 부분 삭제.
- 120–145분: 제품 핵심 과업 1개, 관찰과 가정, 역질문 2개.
- 145–165분: 무작위 질문 10개를 녹음하고 길이·사실 점검.
- 165–180분: 링크·PDF·장비·일정·입사 가능일·연봉 범위 정리.

내일이라도 모르는 경험을 만들어 외우는 데 시간을 쓰지 않습니다. 자신 있는 두 사례와 정직한 한계 설명이 우선입니다.

## 6. 60분 모의면접 시나리오

본인 혼자 연습할 때는 질문만 먼저 읽고 녹음을 켭니다. 답변을 읽으며 모의면접을 진행하지 않습니다.

### 0–5분 / 도입

1. 1분 자기소개를 해주세요.
2. 왜 업종을 바꾸려고 하나요?
3. 총경력과 제품 설계 경험은 각각 어느 정도인가요?

### 5–15분 / PT

플랫폼+TBM 10분. 상대가 질문하면 “질문 답변 후 남은 발표를 줄이는” 방식도 연습합니다.

### 15–30분 / 꼬리 질문

4. 메뉴 구분은 기획자가 했는데 본인 고유 기여는 무엇인가요?
5. 반투명안이 좋다는 근거가 사용자 실험이 아니라면 어떻게 판단했나요?
6. 지도 배경이 밝아지면 어떻게 되나요?
7. 내부 동료 의견과 사용자 검증의 차이는 무엇인가요?
8. TBM에서 저장 실패까지 설계했나요?
9. 서명이 저장되면 일지도 제출된 건가요?
10. HWP 열람의 어떤 부분을 직접 개발했나요?
11. 성과 지표가 없는데 개선이라고 말할 수 있나요?

### 30–40분 / 경력 수준·제품 판단

12. 6년 이상인데 성과 실험 경험이 부족한 이유와 보완 계획은요?

14. 다음 프로젝트에서 성공 기준을 무엇으로 정하겠어요?
15. 사용자 수가 적은 B2B 서비스에서 A/B 테스트를 하겠어요?

### 40–50분 / 협업·컬처핏

## 7. 모의면접 채점표

실제 채용 점수나 합격 예측 도구가 아닌 **연습용 기준**입니다. 각 항목 0–2점, 총 20점입니다. 사실 오류가 있으면 총점과 관계없이 먼저 수정합니다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 직접 답변 | 질문과 다름 | 답이 뒤에 나옴 | 첫 문장에 답함 |
| 역할 구분 | 팀 성과를 독점 | 역할이 모호 | 내 결정·협업 범위 분명 |
| 문제 근거 | 추측을 사실화 | 근거 약함 | 실제 자료/관찰 경로 구분 |
| 선택 이유 | 취향만 설명 | 기준만 나열 | 대안·기준·손실 설명 |
| 결과 설명 | 허위 수치/출시 | 결과·의도 혼동 | 산출물·사용·측정 구분 |
| 경계 인식 | 미수행을 완료로 | 한계만 말함 | 한계와 다음 확인 연결 |
| 제품 사고 | 화면 나열 | 사용자 언급 | 과업·지표·우선순위 연결 |
| 구현 사고 | 정상 화면만 | 예외 이름만 | 상태·정책·협의 항목 설명 |
| 회사 맞춤 | 어디든 같은 말 | 제품명만 교체 | 사용자/과업/기여 근거 |
| 전달력 | 너무 길고 방어적 | 일부 반복 | 60초 안 핵심·사례·결론 |

자가 연습 목표는 16점 이상을 안정적으로 내는 것입니다. 이 수치는 채용 합격선이 아닙니다. 점수를 올리려고 사실을 과장하지 않습니다.

## 9. 면접 직후 10분 회고

| 기록 | 적을 내용 |
|---|---|
| 질문 원문 | 기억나는 표현 그대로 |
| 내 답변 | 어떤 사례를 어떤 길이로 말했는지 |
| 근거의 빈틈 | 역할·결정·성과 중 무엇을 재질문했는지 |
| 다음 수정 | 바꿀 첫 문장 하나·보여줄 화면 하나 |
| 회사 적합도 | 실제 업무와 도메인 전환 목표가 맞는지 |
| 후속 일정 | 요청 자료·기한·담당자 |

면접관의 표정만으로 합격/불합격을 단정하지 않습니다. 답하지 못한 기술을 전부 공부하기보다 같은 질문에서 반복해서 생기는 근거의 빈틈부터 보완합니다.

## 10. 최종 제출·발표 전 확인

- 공고의 회사명·직무·필수 요건과 맞는 자료인가.
- 실제 기간과 직함, 재직 상태가 이력서·PDF·웹·말에서 같은가.
- 플랫폼·TBM 배포, ERP 미사용, 인트라넷 미배포, 칸반 미평가가 정확한가.
- 숫자·색·목업이 실제 운영 성과처럼 읽히지 않는가.
- 공개용 재구성과 원래 작업의 구분을 설명할 수 있는가.
- Figma·코드·시연에서 직접 설명 가능한 범위만 제시하는가.
- 사용자에게 공개할 수 없는 내부 데이터나 소스를 추가로 가져오지 않았는가.
- PDF와 웹의 화면 차이는 설명 가능한가.
- 회사가 별도 발표 덱을 요구하면 기존 PDF만으로 대체하지 않았는가.
- 링크·화면 공유·로컬 PDF·예비 파일이 열리는가.
- 회사별 지원 동기와 역질문이 완성됐는가.
- 발표 시간과 질문 시간을 구분했고 핵심 두 사례를 시간 안에 끝낼 수 있는가.
