# 포트폴리오 PT 발표 대본

## 1. 발표 운영 방식

기본 구성은 **통합 플랫폼 + TBM**입니다. 실제 배포 사례에서 내가 결정한 내용을 보여주는 조합입니다. ERP는 B2B SaaS·운영 도구·데이터 UX 공고에서 확장 사례로 추가합니다. 산업 자체에 관심을 고정시키지 않도록 제목 다음에는 “탐색”, “기록”, “확인 상태”, “자료 조회”라는 보편적인 과업으로 설명합니다.

이 문서는 발표 대본이며 새로운 슬라이드 파일은 아닙니다. 현재 PDF를 보며 발표할 때는 아래 페이지를 사용합니다. 기업에서 별도 발표 덱, 사례 수 또는 특정 양식을 요청하면 그 안내가 우선입니다. 웹만 있는 반려동물·반응형 사례는 별도 탭에 준비합니다.

| 발표 시간 | 추천 범위 | 운영 |
|---|---|---|
| 3분 | 자기소개 + 플랫폼의 핵심 결정 | 4·8·10쪽, 나열 금지 |
| 5분 | 플랫폼 2분 + TBM 2분 + 도입/마무리 | 아래 5분 압축 대본 |
| 10분 | 플랫폼 4분 + TBM 4분 + 도입/마무리 | 기본 대본, 리허설로 속도 조정 |
| 15분 | 기본 + ERP 3분 + 공통 UI 2분 | 도메인과 역할에 맞춰 하나를 줄여도 됨 |
| 20분 | 15분 + 사례 깊이·검증 계획 5분 | 질문 시간을 발표 시간에 포함하는지 사전 확인 |

표의 시간은 연습 목표입니다. 소리 내어 읽어 실제 시간을 측정한 뒤 문장을 줄입니다. 10분을 맞추려고 급히 읽지 말고 화면을 가리키고 잠깐 멈추는 시간을 포함합니다.

## 2. 기본 10분 대본

### 0:00–0:45 / PDF 1–3쪽 / 소개와 발표 범위

> 안녕하세요. 복잡한 업무를 사용자가 이해하고 처리할 수 있는 화면으로 만드는 디자이너 이한울입니다.
>
> 웹디자인과 퍼블리싱으로 시작해, B2B 플랫폼과 모바일 업무 서비스의 UX/UI로 경험을 넓혔습니다. 오늘은 두 가지 사례를 중심으로 말씀드리겠습니다. 첫 번째는 지도 위에서 필요한 기능을 찾도록 메뉴를 구체화한 플랫폼이고, 두 번째는 종이 기록을 모바일 작성과 웹 조회로 옮긴 서비스입니다.
>
> 두 사례 모두 제가 직접 판단한 UI와 구현 범위, 확인한 결과를 나눠 설명드리겠습니다.

화면 동작: 목차 전체를 읽지 말고 4쪽으로 바로 이동합니다.

### 0:45–1:30 / PDF 4–5쪽 / 플랫폼의 문제와 담당 범위

> 첫 번째는 통합 관리 플랫폼입니다. 여러 업무 자료를 지도와 메뉴에서 확인하는 제품입니다. 현업에서는 여러 파일과 프로그램을 함께 살펴봐야 했고, 초기 화면에서는 어떤 기능이 어느 업무에 속하는지 구분하기 어려웠습니다.
>
> 이 중 제가 다룬 과제는 업무별 메뉴와 지도 탐색 UI였습니다. 자료의 최종본을 관리하는 기능을 새로 만든 프로젝트는 아닙니다. 기획자·개발자·엔지니어와 조율하면서 메뉴와 지도 탐색 화면을 설계하고 HTML·CSS·SCSS로 퍼블리싱했습니다.

면접관이 보는 점: 문제의 크기를 실제 맡은 범위로 좁혀 말하는지.

### 1:30–2:15 / PDF 6–7쪽 / 협업과 사용 흐름

> 작업 중 기획자가 기능을 현장 설명과 사업 관리로 나누는 방향을 제안했습니다. 저는 이 구분을 실제 화면에서 어떻게 읽히게 할지 구체화했습니다. 지도와 별개인 메뉴를 만드는 것보다, 위치를 확인한 상태에서 업무 메뉴를 고르고 관련 자료로 이어지게 구성했습니다.
>
> 화면의 세 영역을 보시면, 첫째는 현재 확인 중인 위치, 둘째는 업무 기능을 고르는 메뉴, 셋째는 선택한 기능의 자료 유형입니다. 예를 들어 위치를 확인하고 시뮬레이션 메뉴에서 공정이나 주행 자료를 선택하는 순서입니다. 사용자가 현재 맥락을 유지하면서 자료의 종류를 바꿀 수 있도록 역할을 나눴습니다.

가리킬 곳: 7쪽의 위치 → 메뉴 → 자료 선택. 클릭 수를 세어 성과로 말하지 않습니다.

### 2:15–3:30 / PDF 8쪽 / 내가 한 핵심 결정

> 가장 설명드리고 싶은 결정은 메뉴의 배경 표현입니다. 같은 메뉴 구분을 흰색, 검정, 반투명 검정의 세 안으로 비교했습니다.
>
> 흰색안은 메뉴의 경계를 선명하게 만들 수 있지만 지도와 별도 영역처럼 보였습니다. 검정안은 메뉴의 존재감이 강했지만 배경을 많이 가리는 느낌이 있었습니다. 저는 메뉴를 알아볼 수 있어야 한다는 요구와 지도의 연속성을 함께 고려해 반투명 검정안을 선택했습니다.
>
> 여기서 제가 한 일은 단순히 어두운 색을 고른 것이 아니라, 메뉴와 배경의 관계를 비교하고 업무 구분과 선택 상태가 보이도록 구현한 것입니다. 당시 세 안을 사용자 실험으로 검증한 것은 아닙니다. 시안 비교와 협의로 결정한 내용입니다.
>
> 지금 다시 확인한다면 지도 배경이 밝거나 복잡해졌을 때도 글자와 선택 상태가 충분히 구분되는지를 우선 보겠습니다. 메뉴 자체의 구분뿐 아니라 실제 배경 위에서 읽히는지가 이 선택의 중요한 조건이기 때문입니다.

핵심: **선택 → 기준 두 가지 → 대안의 장단점 → 한계**. 취향 설명으로 끝내지 않습니다.

### 3:30–4:15 / PDF 9쪽 / 다른 자료에서도 이어지는 구조

> 자료 유형이 달라도 같은 원칙을 이어가도록 구성했습니다. 이 화면에서는 영상 분류, 선택 영상의 미리보기, 관련 영상 목록을 구분했습니다. 사용자는 어떤 자료를 보고 있는지와 다음에 선택할 수 있는 자료를 같은 화면에서 확인할 수 있습니다.
>
> 지도 화면과 영상 화면의 내용은 다르지만, 현재 맥락을 보여주고 다음 탐색을 연결한다는 설계 기준은 같습니다. 저는 이런 기준을 시안과 퍼블리싱에서 구체화했습니다.

시간이 부족하면 이 부분을 한 문장으로 줄이고 10쪽으로 이동합니다.

### 4:15–5:00 / PDF 10쪽 / 결과와 한계

> 플랫폼은 배포 후 실제 사용자가 이용했고, 산출물은 시연과 내부 소통, 전시에도 활용됐습니다. 내부 동료에게는 메뉴가 나뉘어 구분이 명확하다는 의견을 받았습니다.
>
> 다만 이 의견은 현장 사용자를 직접 대상으로 한 사용성 테스트 결과와는 구분하고 있습니다. 탐색 시간이나 클릭 수가 얼마나 바뀌었는지는 측정하지 않았습니다. 다음에 같은 과제를 맡는다면 특정 자료를 찾는 과업을 정하고, 첫 메뉴 선택의 성공 여부와 망설인 구간, 완료 시간을 함께 확인하겠습니다.
>
> 이 프로젝트에서는 기획의 방향을 실제 화면의 차이로 만들고 구현까지 연결한 경험을 얻었습니다.

### 5:00–5:45 / PDF 11–12쪽 / TBM의 과업과 역할

> 두 번째는 TBM, 작업 전 안전 점검 기록 서비스입니다. 산업 용어를 빼고 보면 여러 사람이 기록하고 확인한 내용을 보관·조회하는 업무 서비스입니다.
>
> 종이 기록의 보관과 손글씨 판독 문제에 대응하면서, 현장에서는 모바일로 작성하고 웹에서는 자료를 확인할 화면이 필요했습니다. 저는 모바일 일지와 서명 화면의 기획·디자인, 웹 UI에 참여했습니다. 이후 추가된 파일 열람 기능은 디자인과 퍼블리싱을 맡았습니다.
>
> 공개 자료는 가상 데이터와 설명용 재구성 화면입니다. 설계 의도를 보여주는 자료와 실제 배포 사실을 나눠 설명드리겠습니다.

### 5:45–6:55 / PDF 13쪽 / 일지의 정보 위계와 상태

> 일지에서는 우선 지금 어떤 기록을 작성하는지 알아야 했습니다. 그래서 작성일과 출역 인원을 상단에서 확인하도록 했습니다. 다음으로 담당자와 현장 책임자의 확인 상태, 근로자가 확인해야 하는 항목을 구분했습니다. 하단에는 다음 입력 단계로 이동하는 작성하기 버튼을 배치했습니다.
>
> 제가 구분한 것은 작성 맥락, 사람별 확인 상태, 다음 행동입니다. 정보가 입력돼 있다는 사실과 확인이 끝났다는 사실은 다르기 때문에, 동일한 완료 상태처럼 보이지 않도록 구성했습니다.
>
> 다만 버튼을 눌렀을 때의 모든 저장·권한·서버 동작을 제가 개발한 것은 아닙니다. 화면에서 표현할 상태를 구체화하는 것이 제 역할이었고, 실제 구현과 정책은 개발자와 맞춰야 하는 영역입니다. 지금 보완한다면 필수 확인 누락과 저장 실패 시 사용자가 무엇을 수정해야 하는지까지 이어서 살펴보겠습니다.

### 6:55–7:55 / PDF 14쪽 / 서명 입력과 완료의 차이

> 서명도 같은 원칙으로 다뤘습니다. 서명을 입력하거나 변경하는 화면과, 저장이 완료됐다는 메시지를 분리했습니다. 사용자가 화면에 서명이 보인다는 이유만으로 저장까지 끝났다고 생각하지 않도록 결과를 알려주는 구성입니다.
>
> 여기서 서명 저장 완료는 마이페이지의 서명 정보가 저장됐다는 의미입니다. 이것이 일지 전체가 제출되거나 승인됐다는 의미는 아닙니다. 실제 제품에서는 어떤 대상의 작업이 완료된 것인지 메시지의 범위를 맞추는 것이 중요하다고 생각합니다.
>
> 다시 검증한다면 서명을 입력하지 않았을 때, 저장에 실패했을 때, 작성 중 다른 화면으로 이동할 때 사용자가 상태를 어떻게 이해하는지 확인하겠습니다. 이 예외 흐름을 모두 검증했다는 의미는 아니고, 다음으로 보완할 우선순위입니다.

### 7:55–9:00 / PDF 15쪽 / 추가 요청과 범위 확장

> 이후 담당자가 각자의 PC에서 파일을 따로 여는 대신, 사이트 안에서 관련 자료를 보고 싶다는 요청을 전달했습니다. 초기의 일지 작성·업로드에 더해 PDF와 HWP 파일 열람 UI의 디자인과 퍼블리싱을 추가했습니다.
>
> 이때 제가 맡은 부분은 파일 목록과 문서를 보는 화면입니다. HWP 변환 기술이나 파일 처리 엔진을 직접 개발한 것은 아닙니다. 사용자가 문서로 이동하고 내용을 확인하는 화면을 구체화했습니다.
>
> 서비스는 배포 후 실제 사용으로 이어졌고, 사용자 의견은 개발자를 통해 전달받았습니다. 따라서 직접 인터뷰로 발견한 요구라고 말하지 않고 전달 경로를 명확하게 설명하고 있습니다. 다음에는 요청의 배경과 사용 빈도, 기존 방식의 어려움을 직접 확인해 우선순위 판단의 근거를 더 확보하고 싶습니다.

### 9:00–10:00 / PDF 26쪽 / 공통 역량과 지원 역할 연결

> 두 사례의 공통점은 복잡한 업무를 한 화면에 많이 넣는 것이 아니라, 사용자가 지금 무엇을 보고 있고 어떤 상태이며 다음에 무엇을 해야 하는지를 구분한 것입니다.
>
> 플랫폼에서는 지도 맥락과 메뉴 선택을, 기록 서비스에서는 작성 맥락과 확인·저장 상태를 다뤘습니다. 저는 이 구조를 UI와 퍼블리싱으로 구체화하고, 기획자와 개발자 등 여러 직군이 구현 기준을 맞출 수 있도록 협업했습니다.
>
> 다음 환경에서는 이 경험을 다른 산업의 제품에도 적용하고 싶습니다. 초기부터 사용자의 핵심 과업과 성공 기준을 함께 정의하고, 출시 후 실제 사용 결과를 확인하면서 개선하는 역할로 이어가겠습니다. 감사합니다.

## 3. 15분 확장 대본

기본 10분 대본에서 마지막 마무리 전에 넣습니다. 발표 주도권은 유지하되 질문이 들어오면 핵심부터 답하고 돌아옵니다.

### +3분 / PDF 16–19쪽 / ERP

> 세 번째는 비용·인원 ERP입니다. 이 사례는 최종 웹 설계안이 사용되지 않았다는 결과부터 말씀드리겠습니다. 저는 웹 UI를 설계하고 퍼블리싱했지만, 최종 제공 형식이 PDF로 바뀌었습니다.
>
> 설계 과제는 날짜·인원·프로젝트·시간·비용이 행 단위로 기록된 자료를 조회 목적에 맞게 정리하는 것이었습니다. 전사·프로젝트·개인이라는 조회 범위를 구분하고, 조건 설정 다음에 주요 수치와 현황 요약, 필요한 상세 내역을 확인하도록 구성했습니다. 이 범위 구분을 접근 권한 체계와 동일하게 설명하지는 않습니다.
>
> 18쪽을 보면 조회 조건, 요약, 상세의 순서입니다. 사용자가 어떤 조건에서 나온 숫자인지 알 수 있어야 요약 수치와 상세 내역을 연결해서 해석할 수 있다고 판단했습니다. 19쪽에서는 선택 메뉴, 합계, 기준을 넘긴 상태를 구분했습니다. 색상뿐 아니라 숫자와 문구의 강조를 개발자와 공유했습니다. 화면의 이름과 금액, 9시간/기준 8시간은 상태 설명용 가상 예시입니다.
>
> 이 사례에서 확인한 결과는 웹 UI와 퍼블리싱 산출물입니다. 최종 사용이나 업무 효율 개선으로 연결됐다고 말씀드릴 수는 없습니다. 제가 배운 것은 데이터가 어떻게 보일지만큼 어떤 형태로 소비될지도 초기에 확인해야 한다는 점입니다. 다시 시작한다면 누가 어떤 주기로 직접 조회하는지, 누가 정해진 보고서를 받아야 하는지와 최종 제공 형식을 먼저 합의하고, 그 결과에 맞춰 인터랙티브 웹과 보고서 중 우선순위를 정하겠습니다.

화면 체류: 16쪽 20초 → 17쪽 30초 → 18쪽 60초 → 19쪽 70초. 실제 발화 속도에 따라 멈추는 시간을 조절합니다.

### +2분 / PDF 20–23쪽 / 공통 UI

> 마지막은 공통 UI 기준과 웹 가이드입니다. 범위를 정확히 말씀드리면 전사 디자인 시스템 운영 사례가 아니라, 공통 컬러와 일부 입력·검색 UI를 정리하고 재사용한 사례입니다.
>
> 컬러 값은 SCSS 변수로 정의하고 웹 가이드에서 같은 기준을 참고하도록 했습니다. 입력 UI에서는 읽기 전용과 편집 가능한 상태를, 검색에서는 기본·포커스·입력 중·비활성을 구분했습니다. 공통 기준을 유지하되 화면의 맥락에 따라 입력 영역의 크기와 배치는 조정했습니다.
>
> 컬러와 일부 UI 요소는 디자이너의 디자인·프론트 작업에서 재사용했습니다. 다만 조직 전체의 도입률이나 제작 시간 감소는 측정하지 않았습니다. 더 확장한다면 새 컴포넌트 수를 늘리기보다 실제로 중복되는 요소와 상태를 먼저 확인하고, 사용 기준과 예외, 변경 시 영향을 받는 화면을 함께 관리하겠습니다.
>
> 저는 공통 기준을 정하는 것과 개별 화면에 맞게 적용하는 것을 함께 다룬 경험으로 이 사례를 설명하고 싶습니다.

## 4. 5분 압축 대본

### 시작 / 25초

> 안녕하세요. 업무의 정보와 상태를 사용자가 이해하고 처리할 수 있는 화면으로 만드는 이한울입니다. 웹디자인·퍼블리싱에서 B2B 서비스 설계로 경험을 넓혔습니다. 배포 경험이 있는 두 사례에서 제가 한 판단과 결과를 말씀드리겠습니다.

### 플랫폼 / 2분 / 4·8·10쪽

> 통합 플랫폼에서는 초기 메뉴에서 기능의 업무 분야를 구분하기 어려웠습니다. 기획자가 현장 설명과 사업 관리로 나누는 방향을 제안했고, 저는 이를 지도 위의 메뉴 UI로 구체화하고 퍼블리싱했습니다.
>
> 핵심 결정은 메뉴의 배경 표현입니다. 흰색안은 경계가 분명하지만 지도와 분리돼 보였고, 검정안은 메뉴 존재감이 강했습니다. 저는 메뉴 구분과 지도 배경의 연속성을 함께 고려해 반투명 검정안을 선택했습니다. 또 위치 확인, 업무 메뉴 선택, 자료 유형 선택의 역할을 나눴습니다.
>
> 플랫폼은 배포 후 실제 사용됐고 내부 동료에게 메뉴 구분이 명확하다는 의견을 받았습니다. 현장 사용자 테스트나 클릭 수 감소를 측정한 것은 아닙니다. 다음에는 같은 자료 찾기 과업으로 첫 선택과 완료 시간을 확인하겠습니다.

### TBM / 2분 / 11·13·14·15쪽

> TBM은 작업 전 점검 내용을 기록·확인·보관하는 서비스입니다. 저는 모바일 일지와 서명 화면을 기획·디자인하고 웹 UI에 참여했습니다.
>
> 일지에서는 작성일과 출역 인원으로 작성 맥락을 먼저 확인하고, 담당자·현장 책임자의 확인 상태와 작성 버튼을 구분했습니다. 서명에서는 입력·변경과 저장 완료를 분리했습니다. 서명 정보의 저장이 일지 전체의 제출 완료로 오해되지 않도록 완료 범위를 정확히 다루는 것이 중요합니다.
>
> 이후 사이트 안에서 파일을 보고 싶다는 요청에 따라 PDF·HWP 열람 UI의 디자인과 퍼블리싱도 추가했습니다. 파일 처리 엔진 개발은 제 범위가 아닙니다. 서비스는 배포 후 사용됐고 사용자 의견은 개발자를 통해 전달받았습니다. 공개 화면은 설명용 재구성이며, 업무 시간 감소를 측정한 자료는 없습니다.

### 마무리 / 35초

> 두 사례에서 저는 업무의 맥락과 다음 행동을 구분하고 구현 기준으로 구체화했습니다. 새로운 산업에서도 기록·조회·상태가 복잡한 문제를 정리하는 데 기여할 수 있습니다. 앞으로는 설계 초기에 성공 기준과 확인 방법을 정하고, 실제 사용자 피드백과 결과를 다음 개선으로 연결하는 책임을 넓히고 싶습니다. 감사합니다.

5분 대본은 발화량에 따라 4분대로 끝날 수 있습니다. 남는 시간은 화면의 핵심 영역을 가리키며 설명하되 새 프로젝트를 급히 추가하지 않습니다.
